# Excel 读取适配（#148）

`readPlatformExport` 与 `parseLittleGiantWorkbook` 使用固定版本
`documonster@0.20.2` 的 `documonster/excel` 公共命名空间，
并通过公共 `documonster/archive`、`documonster/xml` 核对来源元数据。
文件身份、首张工作表选择、列位、行号、原字段、警示和领域规则沿用原契约。
缺文件、损坏包、缺工作表均抛错；有效的空工作表仍返回空解析结果。

`lib/excel-read-value.ts` 只适配原读取器已使用的单元格值：

- 富文本、超链接、合并值、普通数字和布尔值继续交给原文本转换规则。
- 不执行公式，也不推算缺失缓存。ExcelJS 4.4 读取时省略的公式缓存
  `0`、`false`、空字符串保持旧的非空未知文本 `[object Object]`。
  普通单元格的 `0`、`false` 仍分别是 `0`、`false`。
  这是迁移兼容行为，不表示这些缓存不存在，也不把未知值改为空值。
- 识别为日期的现代数字日期和 1904 纪元保持原结果及毫秒舍入。平台表仍输出 ISO 日期，
  小巨人表仍使用原来的 `String(Date)`（含运行环境时区）。

## 转义单位格式的已核实差异

基线 `a9bc61f79104a0ccbadf1a7b0a3258efd4f8327f` 与迁移集成
`987027925b833fa0e4c4a0d1ba5b0df0900a663c` 的两个完整公开解析入口，
对数字 `45200` 使用 `0\m` 或 `\m0` 时存在以下差异：

- 普通数字及数值公式缓存：旧 ExcelJS 4.4 识别成 Date，平台原字段为
  `2023-10-01`，历史表原字段为该日的 `String(Date)`；新读取器保留数字，
  两个入口均输出 `45200`。
- 普通文本 `45200`、文本 `=45200` 两版相同；公式不执行。
  缺缓存公式两版仍为非空未知文本 `[object Object]`，不变成数字或空白。
- 文本公式缓存也不能笼统声称相同：缓存字符串 `45200` 被旧库转成日期，
  新库保留文本；缓存 `第1批` 时旧库产生 Invalid Date，平台转换抛错，
  历史批次列报未知批次；新库保留已有的 `第1批`，历史解析及请求构造器
  因而多保留该合成源行的一条 2019 年认定事件。这不是计算公式或补猜批次。

这里的反斜杠把 `m` 标为字面单位，而非月份。旧库去掉引号和方括号后
检查日期字母，却没有排除转义字母；新库识别转义，因此保留数字有具体的
格式依据。解析器输出原值文本，不负责渲染单位后缀。旧日期输出是兼容基线，
不能单独证明这种单位格式表达了日历日期。`General`、`0"m"` 和真正日期格式
`yyyy-mm-dd` 的数值/数值缓存对照也已独立验证；这些例子不构成任意格式保证。

业务影响按列区分，不能把上述差异仅归为显示变化。三种平台布局的完整解析和
快照载荷验证表明，原字段会改变；位于名称、信用代码、注册地或审核状态列时，
对应转换字段也会改变。合成数值例的行数不变，快照年度仍由调用方提供。
历史表 E:I 的变化只进入原字段；落在 A:D 时可改变序号、属地、名称、信用代码，
并传到请求中的身份字段及出处序号（A 列由旧的 `0` 变为 `45200`）。
数值/数值缓存 `45200` 落在 J 列时，两版都报 `unknown_batch_label`，
不为该行生成事件或年份；其余有效批次的事件数、年份和类型保持。
K 起仍不作为名单字段读取。上述请求构造验证只在内存进行，没有提交业务写入。

本次对选定的三张真实平台表及历史表，通过公共 Archive/XML API 解析格式、
工作簿关系及每一个存储单元格，含表头、空值/样式单元格和名单字段区以外的列。
四表分别扫描 1,000,314、132,342、621,225、16,700 个单元格，
未发现上述两个格式的定义或实际使用。四份源文件的完整 SHA-256、扫描部件哈希、
样式引用统计和读取前后不变证明保留在 Git 外；这不是仅搜索 styles.xml 的结论。
精确旧新源码还分别重跑四份完整解析，与原始独立金样深比较及带类型 JSON 比较
均一致：合计 10,532 行，历史表保留原有 2 项问题。未发现这四份输入的业务回归。

处置为保留转义单位的数字/缓存文本行为，并明确上述兼容差异，不恢复旧日期误判，
不新增格式解码器或修改资格规则。这里不承诺将这两种单位格式当日期使用的
旧输出兼容；真实日期输入仍须有日期格式或来源契约依据。
负向扫描与业务等价结论仅绑定已核对的四份输入，不覆盖其它文件、其它格式或
未检查的缓存类型。若其它必要支持输入确实依赖旧输出，须携来源依据、具体字段
和完整解析差异交回父任务决定最小修复，不能以本节豁免回归。
私有 `parent-compat-disposition-r1/` 留存复现、完整扫描、逐字段处置、命令清单及
源文件/源码绑定；本次仅补文档，不替代父票的最终 HTTP/API、隔离副本或资源验收。

## 早期数字日期

0.20.2 的普通读取模型把 1900 纪元数字序列 60 和 61 都暴露为
`1900-03-01`，`Cell.getDateParts`、`Cell.getModel` 也已没有原序列。
旧库分别暴露 `1900-02-28`、`1900-03-01`；旧库本身不是日历正确性的标准。

公共 `Stream.WorkbookReader` 的 `styles: 'ignore'` 选项仍保留原始数字及
公式缓存。适配器先检查实际使用字段中的早期日期，只在需要时用同一份输入字节
进行这次无样式读取，并按工作表名和单元格位置恢复数字。
这不是从已转换的日期反推序列，也不依赖 ZIP 内工作表出现顺序。
合并从单元格使用公共模型中给出的主单元格地址；读取迭代器完整消费，释放库的
延迟工作表资源。小巨人 A:J 以外的字段不参与日期适配。

恢复到原始数字后，保留旧读取器的线性纪元和毫秒舍入，包括虚构闰日的旧输出。
因此序列 60 与 61、负数、零、时间部分及 1904 纪元无需拒绝或猜测。
遇到需要恢复但原始数字确实不可取得的日期，则带表名、单元格地址抛错，
不会返回成功空表或将其置空。
没有自写 XML/ZIP 编解码器、私有导入、上游补丁或 ExcelJS 运行时回退。
适配错误先记录，完整消费所有工作表后再抛出，确保剩余延迟工作表也触发库的清理。
清理测试在独立的每次调用临时目录里轮询库的异步删除完成，不清理其他调用的目录。

## 原生日期与部件完整性

公共 Excel 模型和无样式 reader 都会把原生 `t="d"` 值变成 Date，丢失原始时区文本。
通过公共 ZIP/XML API 仅取选中工作表的原生日期地址与原文，保留 ExcelJS 4.4 对该原文的
`parseFloat` 行为。例如 `2023-01-01T00:30:00+14:00` 保留数字 `2023`，不能从 UTC
年份反推为 `2022`。有日期样式时沿用旧样式判定、线性纪元与舍入；公式缓存同样适配。
这保留迁移前的输出，不表示旧库把原生日期当数字是日历正确的行为。

读取前从包级关系解析工作簿，再从工作簿关系解析每张声明表的实际部件名，核实部件存在；
不按 sheetId、ZIP 顺序或幸存工作表猜路径。读取后再核对完整的表名与声明顺序。
因此缺首表但仍有空第二表时明确失败；真正空的首表仍保留。
0.20.2 对某些有效的非标准表部件名会漏读，遇到这种不完整模型明确报错，
不以第二表或成功空结果掩盖。不在本切片编写替代 OOXML 读取器。

两个公开解析入口使用独立 ExcelJS 夹具验证富文本、公式、空值、坏文件和表选择；
日期包含两纪元各九例的普通值及缓存值，另覆盖早期日期合并、时间部分、负数
1904 序列和反向 ZIP 工作表顺序。真实四文件的完整原字段、规范化结果、顺序、
问题和元数据对照记录留在 Git 外；源文件、业务数据和测试证据不随代码提交。
