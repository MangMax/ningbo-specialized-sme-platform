# Record comparison read contract (#67)

`GET /api/roster/record-comparison` and MCP `list_record_comparison` require explicit `queryIds`, `exportBatchIds` (may be empty), and `officialSourceDocumentIds`. The REST query accepts repeated or comma-separated IDs. `asOf` caps selected source/decision timestamps; it does not select a latest version or reconstruct past decision states. Optional `enterpriseId`, `titleCode`, and `classification` filter visible event rows. `page`/`pageSize` (1–200) are applied after global counts. Unknown, duplicate, or out-of-scope IDs fail with 400. Both read surfaces return the same service result and `no-store`.

Each `rows[]` item is one formal `award`/`review` event with its original event ID, record, evidence locations, classification, selected correspondences, linked platform rows, and independent later processes. `counts` states its distinct grains. `coverage[]` exposes archived query status, AND conditions, title/page completion and unfinished scope; raw responses and raw fields are omitted. `currentSourceConsistency.recognizedObservations[]` and `exportObservations[]` preserve each selected original row ID. Equal USCC and title produce `same_uscc_title_observed` with both row locations even when definitive qualification is `not_comparable`. No absent edge is interpreted as absent export.

Main event precedence: a confirmed same-event process status contradiction wins; otherwise sufficient confirmed support is aligned; unresolved fact or source scope remains unresolved. A complete archived query covering the exact event subject/title and no confirmed/candidate edge yields `official_without_correspondence`. A later process never changes the event classification. `platform_without_official` requires a verified complete formal scope proof. Definitive `matched`, `interface_only`, `export_only`, and `field_conflict` require a verified interface/export scope and version equivalence proof. Without that proof the read still returns actual positive row observations, and qualification stays `not_comparable`.

`GET /api/roster/record-comparison/legacy-impact` and MCP `preview_record_correspondence_impact` accept the same source set. They return paginated `difference_reason.id` and original status/reason/measure/evidence references, possible event categories, source-row candidates, counts before pagination, unresolved events, `dataIssues`, and `modelIssues`. All old rows remain unchanged; candidate edges require explicit review. No SQL writes, collection, or business-cause inference occurs.

## Proof boundary and minimal extension

Current `source_document` has path/title/date but no complete title/year/enterprise coverage declaration. `import_batch.summary` is an untyped import summary, not an approved complete coverage certificate. `platform_query.collectionEvidence` can prove completed page ranges and actual AND conditions, but `platform_export_batch` has only a date/hash and cannot prove identical account, region, filters, collection window or platform data version. The public routes therefore cannot currently attest complete formal coverage or current-source equivalence. This is an implementation gap for full production qualification, not an implied negative conclusion.

The read service already accepts an optional server-supplied `VerifiedComparisonEvidence` with formal title/year/enterprise/source-document coverage and current query/batch equivalence, bound to query evidence fingerprint and export SHA-256. A stale fingerprint is rejected by the comparison path. The HTTP/MCP adapters do not accept client assertions as trusted proof.

A minimal separately approved persistence addition would store immutable `comparison_scope_proof` rows with ID, proof kind, verified actor/time/basis, selected source document IDs and their file hashes, title/year/enterprise scope and completeness, or selected query ID plus its source fingerprint, export batch ID/SHA-256, exact account/region/filter/collection window and platform version/freeze evidence. The public write capability would require authenticated preflight/commit and append-only audit; the comparison read input could then accept proof IDs, resolve and recheck them server-side, and pass only verified rows to the existing service branch. This ticket does not create that schema or write route.

## UI source picker

`GET /api/roster/record-comparison/sources?kind=query|export_batch|official_document&page=1&pageSize=50` returns `{rows,total,page,pageSize,counts,selection:'explicit',completeness:'not_implied_by_catalog'}`. Each row has `kind,id,label,subtitle,titleCode,titleName,observedAt,status,selectable`; query rows also show `rdjb`, archived completeness/fullRange and effective AND conditions; export rows show SHA-256, row count, and replacement ID; official rows show document title, number, date, and path. A failed export batch is visible but not selectable. Query rows, including partial/failed, remain selectable so users can inspect actual coverage. IDs map directly to `queryIds`, `exportBatchIds`, and `officialSourceDocumentIds`. The catalog is paginated in stable ID order and does not preselect a version or imply that listed documents cover a title/year completely.
