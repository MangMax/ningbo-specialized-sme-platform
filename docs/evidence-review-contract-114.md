# Bounded explanation review contract (#114)

Frozen 2026-10-19 for #111. Depends on #109/#113; no UI or automatic business judgement.

## Read operations (no token, Cache-Control: no-store)

- GET `/api/roster/evidence-impacts` / MCP `list_evidence_impacts`: optional enterpriseId, titleCode, direction, decisionId, eventId; `view=current|historical|all` (current), `state=pending|reviewed|all` (pending), limit 1..100 (50), cursor. Returns `{rows,nextCursor,asOf,projectionReady}`. Rows expose id, exact enterpriseId/titleCode/direction/decisionId, latestRevisionId, reviewedRevisionId, classification (premise_invalid/evidence_changed), pending, lineage (current/historical/withdrawn/merged), oldDecision. No processing on reads. Unknown enterprise list is empty.
- GET `/api/roster/evidence-impacts/:id` / `get_evidence_impact {id}`: exact durable item, oldDecision, live currentDecision (null for merged owner), live evidenceToken, reviewedBaseline (reviewedRevisionId/actor/basis/ruleVersion/effectiveAt/recordedAt, or null), queryCoverage (null for merged owner), gaps and lineage. Since #108 `reviewedBaseline.actor` and `.ruleVersion` may be real `null` meaning “not recorded”; consumers must render that answer, not substitute a placeholder user or a protocol/schema version. Gaps preserve bounded #109 sources/truncated; never claim unknown subjects are zero records. Historical items cannot be completed.
- GET `/api/roster/evidence-impacts/preview` / `preview_evidence_impacts`: required revisionId, optional enterpriseId/titleCode/direction/decisionId, limit/cursor. Only committed revision IDs; evaluates bounded candidate decisions via #113 and returns classification including no_review. No caller-supplied source bodies.
- GET `/api/roster/evidence-impacts/:id/sources` / `list_evidence_impact_sources {id,limit?,cursor?}`: separate source page of scalar committed revision references/classification and eventId; no raw bodies, credentials or free-form source metadata.
- GET `/api/roster/evidence-impacts/revisions/:revisionId/events` / `list_evidence_revision_events {revisionId,enterpriseId?,limit?,cursor?}`: separate exact associated event page.

Cursors are opaque, signed, filter-bound, operation-bound. The first list read holds a read-only SQLite WAL snapshot and freezes committed projection watermark, impact ID ceiling, decision ID ceiling and receipt ID ceiling. Held readers are capped at 64 per process, expire after 120 seconds, and may be evicted at the cap; an expired/evicted cursor returns 400 invalid_cursor and must restart. A single-page read closes its reader immediately. This also freezes inherited legacy ownership/deletion across a concurrent merge without copying full result sets or original archives. Subsequent pages use immutable source links and historical receipts at those ceilings, so processing, replacement, completion and later evidence do not reorder or change the result set. Source/event pages freeze immutable revision ceilings. Cursor tampering/filter changes fail 400; process restart invalidates cursors (start a fresh read). `asOf` describes the frozen result; detail tokens are live and must be reread for completion.

## Explicit work commands (configured write token)

POST `/api/roster/evidence-impacts/commands` / MCP `process_evidence_impacts` accepts `{action:'process',limit:1..100,idempotencyKey,actor:{type:'user'|'agent',id},basis}`. Returns bounded #113 `{processed,unfinished,watermark}` plus command receipt. No startup sweep.
Same POST / MCP `release_evidence_rule` accepts `{action:'release_rule',ruleId,version,scopes:[{enterpriseId,titleCode,direction,previousEvaluationDigest,evaluationDigest}],idempotencyKey,actor,basis}`. 1..50 distinct exact scopes, explicit rule version and SHA256 evaluation digests from the authorized evaluator; identical evaluations create no revision. Same version with different evaluated material conflicts. Does not auto-drain or change business reasons. This is an explicit publication envelope, never a source ingestion endpoint.

## Review completion through existing #102

POST `/api/roster/decision-lifecycle/commands` / existing MCP `save_difference_decision` retains all #102 fields, adding `action:'maintain'` and optional `reviewedEvidence:{latestRevisionId:number,projectionReady:true}` (required for maintain, optional for replace; prohibited for withdraw). Include exact enterprise/title/direction, expectedCurrentId, idempotencyKey, actor,basis,ruleVersion,effectiveAt. Maintain omits decision and preserves the original version/reason/measure/evidence/audit. Replace supplies an actual #102 decision; no invented replacement. Both actions check live current decision ID, latest relevant committed evidence revision and projectionReady inside the existing immediate transaction, then record baseline and original receipt atomically. Withdrawn/historical/merged owners cannot be maintained. No evidence baseline means unknown, never valid.

Receipts retain #102 fields `{versionId,currentId,previousId,action,recordedAt}` and review completions add reviewedRevisionId. Same key/same request replay returns original receipt before concurrency checks and makes no writes; it cannot clear later evidence. Same key/different request:409 idempotency_conflict; changed decision:409 stale_version; changed/unprocessed evidence:409 stale_evidence. Failure rolls back decision, baseline and receipt together. Read detail again after conflict. API/MCP use existing auth, structured error codes, credential filtering and no-store semantics.

#109 queryCoverage/currentDecision/explanationValidity/assessment shapes remain intact. Validity adds valid/evidence_changed. Persisted pending state precedes no-baseline unknown; a reviewed baseline is valid when the scoped projection is ready and the decision has no substantive pending impact. A broader scoped token may advance for coverage-only changes or disjoint partitions evaluated as no_review; this does not create a task, review receipt, or baseline advancement. Failed/partial coverage remains independently observable. New unprocessed changes conservatively report evidence_changed, and a later no_review change never clears an earlier substantive pending impact. Completion still checks the exact live token and readiness inside #102, and successful receipt replay remains unchanged. A reviewed old not_queried premise can be explicitly acknowledged without altering the business reason. No production migration/backlog work is authorized.

Migration 0024_evidence_review_114 adds immutable command/review receipts and exact rule-release version pins (including unchanged evaluations), journal idx24 timestamp1792400021005 (idx23 reserved for refreshed #113). No historical backfill.


Explicit maintain of a legacy version adopts that coordinate through its review receipt. Existing #102 import, legacy annotation and managed-merge guards recognize it; they preserve original version IDs, reason/measure and scope. Unreviewed legacy merges retain historical impact scope; detail marks the removed owner as merged, returns currentDecision=null, and shows the surviving owner on oldDecision. Completion on a removed owner is 404. Replacements settle the observed source version and establish the resulting version baseline in the same transaction.

Integration for this slice includes pinned #107 e343179 through #108 71d22a008a6af7db9e2ea43c0ea9177213318bea. #103 fact changes, evidence revision capture, batch finalization and terminal receipt are atomic; failed finalization rolls all of them back. This slice does not change that outer transaction or copy upstream fixes.

Legacy duplicate consolidation can remove an unreviewed legacy decision row under the inherited merge contract. Such a historical item retains its original impact ID and decisionId, with oldDecision=null and gaps.decisionUnavailable=true; the survivor's decision is never substituted. Reviewed/managed versions are protected by the existing merge conflict gate. This is an explicit historical evidence gap, not a new business conclusion.

Held list snapshots are rolled back and their read-only connection is closed on eviction, 120-second expiry, initial anchor/read failure, and the existing Nitro close hook. Idle timers use unref() and are cancelled when the reader closes. No reader/result is serialized to disk. Until readers close, SQLite may retain WAL frames under concurrent writes; max64/TTL120 bound reader count/lifetime, not WAL bytes or production write volume. No production-load/WAL-size certification is claimed.

## Browser review capability (#108, transitional)

The daily review form no longer collects a write credential, an operator name or a rule version. Those are not business facts; a hand-typed `admin`/`v1` would permanently write a false operator and a false rule version. The background HTTP/MCP command contract above is unchanged and still requires `actor` and `ruleVersion`.

- GET `/api/roster/evidence-review/browser-context` returns only `{writeEnabled:boolean}` with `Cache-Control: no-store`. It never returns the token, an actor, a session or a configuration value. `writeEnabled` is true only when **both** `NUXT_API_TOKEN` is non-empty and `NUXT_BROWSER_REVIEW_ENABLED=true`.
- POST `/api/roster/evidence-review/browser-commands` accepts only `maintain`/`replace` business fields: exact scope, `expectedCurrentId`, `idempotencyKey`, `basis`, `effectiveAt`, optional `reviewedEvidence`, optional `decision`. `actor` and `ruleVersion` are rejected by the strict schema; sending either is 400. The route writes through the same single #102 transaction/service as the external command — it is not a second writer.
- This is an explicit deployment capability (“allow this application's browser to submit a human review”), **not login authentication**. It identifies nobody and creates no session. It does not treat same-origin as an identity: with the switch off, same-origin requests are rejected too. The token is only the existing write-enabled prerequisite; it is never compared to a browser header, returned, or stored in cookies/Web Storage. #127 replaces this capability with the real permission model.
- Request gate: the deployment switch and configured token; `Sec-Fetch-Site` must be absent or exactly `same-origin`; `Origin` is required and must exactly equal the server-normalized request origin (raw `Host` + connection protocol; forwarded host/proto headers are ignored); content type must be `application/json`. Missing `Origin` (curl/MCP), cross-site, mismatched origin and wrong content type are rejected before reading the body or writing. No permissive CORS headers are emitted.
- Persisted `actor`/`ruleVersion` for browser reviews are real JSON `null` on both the decision version and the review receipt. The receipt column stays SQL `NOT NULL`; Drizzle serializes JSON null to the text `'null'`, verified against real SQLite. No `unknown`/`system`/`admin`/`未记录` string is stored as an operator, and no protocol/schema/software version is substituted for a business rule version. The idempotency request hash covers the complete internal command including those nulls, so retries remain identical.
- Historical receipts keep their original actor/rule text unchanged. Read models may express null; consumers display `操作人：未记录` / `业务规则版本：未记录` without inventing a person or a version.
