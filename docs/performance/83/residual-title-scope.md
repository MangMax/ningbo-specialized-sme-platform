## Archived shape and write semantics

The old predicate evaluates `json_each(json_extract(collection_evidence,'$.titleScope.rdjb'))`. A synthetic historical-data differential runs that predicate **before migration**, then compares the new public reader after migration for SQL NULL, JSON null, numeric/boolean scalars, missing scope, digit-string scalar, JSON-array-string/JSON-text-string scalars, object, array, mixed nested/nontext array elements, invalid outer JSON, invalid scalar JSON, and a direct-title row with malformed JSON. It checks IDs or the exact `malformed JSON` error. The digit-string case is significant: the old second JSON parse treats `"2"` as numeric 2, not text membership; the new table preserves that outcome. Bad archive text on a direct-title row still returns that row. Synthetic tests also verify post-migration valid/malformed insert, archive repair, malformed-row delete, archive update, delete, and rollback of an archive update in the same transaction. The production-distribution backup contains no malformed marker rows, so malformed-shape parity is proven by synthetic regression, not by this backup's public hash.

The reversible synthetic write probe (`node scripts/bench-platform-title-scope-write.mjs`) uses seven alternating before/after rounds of 300 inserts, 300 archive updates, then 150 deletes per rollback-only transaction. Median write-phase sum was 1.26 ms before and 15.21 ms after; median update phase 0.19 vs 7.12 ms, delete phase 0.30 vs 5.44 ms. All transactions rolled back to zero query/membership rows. These tiny local file-backed synthetic timings show nontrivial trigger/index write amplification, not production write throughput; parent migration review should retain this cost. A fresh replay on the resumed candidate measured 1.35 ms before versus 16.66 ms after (update 0.20 versus 7.64 ms; delete 0.32 versus 5.70 ms), again with zero rows after rollback; exact output is `/tmp/ningbo-perf-83-current/write-cost-resume.json`. The new index and triggers cannot be treated as free.

Migration rollback requires pairing the prior application binary with the untouched pre-0025 SQLite backup. The operator procedure is: (1) stop every app/pipeline writer and serving process; (2) make a consistent checkpointed backup and retain its checksum plus the prior binary before applying 0025; (3) if rollback is required, restore the complete database and its consistent journal state, then start the prior binary; (4) verify integrity/FK checks, the 25-entry ledger, original row counts/hash, and a public full/summary/raw read before reopening writes. Do not transplant an old main database file alongside a newer WAL. Dropping the derived tables while new code serves title reads would break those reads. Any writes accepted after the backup require a separate recovery plan; restoring that backup alone would discard them. The untouched source clone was rehashed and integrity/FK checked after migration on its separate copy. This is local backup/restore readiness, not a production rollback drill.
