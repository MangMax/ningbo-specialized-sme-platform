# 统计查询链路性能验证（2026-11-06）

用户要求用 Docker 3482 真实业务副本优化整个统计查询链路。候选基线为 `6f28b70910095020779612bf80b9ac802df7c4a7`；数据为独立只读 SQLite（7,297 家企业、10,464 个企业称号组合），源服务和数据库均未修改。

## 原因与改动

- 年度投影逐企业、称号、年份反复扫描全部事件和出处。使用现有依赖 es-toolkit 的 `groupBy` 建立请求内分组，事件/出处 ID 与文件路径用 Map 查找；分页后才组装出处。区县计数改为单次累加。
- 原统计为每个企业称号读取完整对应来源诊断和平台筛选见证。汇总现在复用同一个 v10 evaluator 的轻量投影；明细分页确定后再调用原完整 reader 补齐诊断、依据和引用。历史年度诊断仍来自原年度规则；当前年度和区县明细保持原完整诊断。
- 明细来源复验曾反复构造、编译复杂 Drizzle SQL。请求内复用绑定参数的预编译语句，每次执行仍重新读取、复验来源与凭据。原64KiB凭据读取边界、分块规则保留。
- 没有跨请求结果缓存、预计算业务表或 schema 迁移。资格裁定、时区、未知时点、迁入限制、稳定排序及分页口径均未修改。汇总与明细仍处于同一读事务和同一 `asOf`。

## 实测

以下为本机 Nuxt 开发服务、同一真实副本；不是生产容量/冷磁盘基准。最初区县45.5秒包含并行浏览器请求，不能把该值当成独立性能倍率。

| 请求 | 优化前观测 | 优化后公开 HTTP |
| --- | ---: | ---: |
| 年度默认请求 | 首次63.0秒；本轮独立复现38.7秒 | 639毫秒 |
| 区县默认请求 | 45.5秒，存在并发竞争 | 399毫秒 |
| 区县按称号请求 | 6.20–6.65秒 | 325–379毫秒 |
| 年度2024专精特新第2页 | 未测 | 436毫秒 |
| 余姚市专精特新第2页 | 未测 | 323毫秒 |

四区块同时请求三轮：897 / 778 / 733毫秒。无统计结果缓存，每轮均执行查询。公布及迁移模块原本较快，本轮未改其业务实现。

## 正确性与回归

- 真实副本13个公开 HTTP 请求与优化前保存的完整 JSON 深比较一致（仅删除自然变化的顶层 `asOf`，其余汇总、排序、分页、说明、出处和引用均比较）。
- 独立固定时点 `2026-11-06T12:00:00Z` 的年度完整响应深比较一致，含 `asOf`；该路径从剖析基线22.7秒降到706毫秒。此数值来自内部剖析 harness，不能冒充公开 HTTP 时间。
- 7文件118测试通过：四个统计 HTTP 文件、`current-qualified-408`、`record-correspondence-refs-r2`、`annual-decision-scope-263`，`--maxWorkers=1`。
- 新增 `prepared_refs_reuse_compilation_without_caching_source_validity_511`：真实重复调用由5次编译降到1次，事件版本变化后诊断仍变为需重核实；原版RED、修复GREEN。
- 新增 `effective_count_projection_preserves_status_and_basis_without_correspondence_reads_511`：来源变化前后，汇总投影与完整判定相同，且不读取对应来源诊断。强化断言后单独重跑1/1通过。
- Typecheck、diff-check通过。UI源码未改，本轮未重复浏览器验收；此前真实副本桌面/390px展示证据单独保留。
