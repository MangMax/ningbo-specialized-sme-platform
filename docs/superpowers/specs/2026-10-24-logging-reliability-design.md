## 目标与现有证据

目标是在正常业务负载下，避免高频诊断挤掉业务事件；在超载或故障时有明确、诚实的反馈，日志故障不改变业务结果。

已证实：同步 Drizzle 调用可以在排空任务获得执行机会之前填满队列。原 FIFO 会因此拒绝后来的任务终态，复现不依赖 SQLite 故障。现有修复已允许高等级替换排队中的低等级事件，但没有减少逐查询事件的放大量。

原生 201 条业务记录链路的串行诊断中，4 个任务均完成且终态存在；仍有 1,929 次 overflow，drainFailures 为 0。另一次与构建并行的运行出现 drain_timeout，具体耗时位置仍 UNKNOWN，不能归因为 SQLite 或主线程阻塞。

这些数据来自 `/tmp/implement-spec-180/log-drop-20261024/`，属于已有验证；本设计尚无新的产品验收结果。

## 方案取舍

| 方案 | 收益 | 代价 / 局限 | 结论 |
| --- | --- | --- | --- |
| 扩大队列、延长超时 | 改动最少 | 延后饱和，增加内存和关闭等待；不减少日志量 | 不作为主要修复 |
| 合并特定重复诊断、及时排空、明确结果 | 处理已证实原因；沿用现有 worker、策略锁和 SQLite | 查询尝试不再一条对应一个日志记录，必须明确计数语义 | 推荐 |
| 增加磁盘缓冲、独立采集服务或更换数据库 | 可以扩大持久化能力 | 新增重放、磁盘容量、去重、部署与运维问题；仍需处理过载 | 当前不做 |

有界批处理本身是常见设计；OpenTelemetry 的 BatchLogRecordProcessor 也规定队列上限及队满丢弃。SQLite WAL 只有一个同时写入者，但本次已证明入队阶段就能发生丢弃，因此先治理事件量与调度，而不是直接换库。

参考：[OpenTelemetry Logs SDK](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/logs/sdk.md)、[SQLite WAL](https://www.sqlite.org/wal.html)。

## 一、只合并重复的 Drizzle 查询尝试

合并在 `LogService` 的现有待写队列内完成，不增加另一套缓存、生产者定时器或公共接入接口。`appLog` 调用方式保持不变。

- 仅匹配内建 Drizzle 观察器的精确形状：system / debug / started、node / drizzle / hook、五种固定 `db.query.*` 操作、七种固定连接用途。已有额外计数或不符合形状的事件不参与。
- 合并键包括除生成的 id、timestamp 外的全部安全事件事实。requestId、traceId、taskId、execution 等任一不同就分开；缺失的上下文保持缺失，不猜测请求归属。
- 只合并尚在队列中的同类项。在途批次不修改；每遇到非合并事件，结束当前合并段，避免跨越业务生命周期事件。不同 SQL 动词各自计数。
- 同一段内重复事件增加 `counts.total`，含义严格为“查询尝试次数”。不是成功次数、影响行数、耗时或 SQL 相同次数。`select` 类包含不同 SELECT，绝不声称它们是同一语句。
- 保留第一条的 id 和 timestamp，详情标明“排队期间查询尝试汇总；时间为首次尝试”。单条也显示次数 1；不增加原始 SQL、参数或错误内容。
- 合并后的序列化字节照常计入队列预算；超过单条/队列预算或安全整数范围时另起一条，走原有入队规则。索引只引用现有队列成员，大小不超过队列条目上限，出队/淘汰/关闭均移除。
- 没有上下文的查询只能称“该进程、该连接用途的查询尝试”，不能称“当前请求查询数”。

这不是采样：参与合并的尝试数完整累计；如果汇总记录本身因故障或过载丢失，仍如实计为丢失，不能声称保住了其中所有尝试。业务事件、HTTP 完成、任务终态、warn/error 均不合并。

用户的来源/集成/最低级别规则继续在 SQLite 写锁内生效，字段投影和 stdout 使用相同授权结果。不用进程内策略缓存提前决定丢弃，避免破坏跨进程配置更新与旧队列重新授权。

## 二、达到批次时尽快排空

- 保留现有 100ms 定时器作为低流量兜底。
- 达到现有批次条目或字节阈值，或进入 warn/error 时，安排一次 `setImmediate` 排空。自定义更小队列使用不超过队列容量的触发阈值。
- 调用方只安排任务，不同步启动 worker、不等待 SQLite。调度合并为一个，保持单个在途写批次；已有 drain 会继续处理新增队列。
- 关闭时取消待运行调度，再执行现有有界 flush。处理 drain 完成与新入队的交接，避免留下无人唤醒的队列。
- 沿用严重度优先替换、1024 条 / 4MiB 待写预算、8192B 单条、64 条 / 256KiB 批次、2s 调用超时、3s 关闭期限。字节预算是序列化负载预算，不是整个进程 RSS 上限。

更早排空不能打断无限同步循环；它与诊断合并各解决一个问题。暂不通过放大预算掩盖问题，也不凭推测修改超时。

## 三、把“丢失”和“未知”分清

状态继续使用现有受保护接口，增加少量计数，不增加配置页上的调优开关。

| 状态 | 含义 |
| --- | --- |
| stored | worker 确认写入的记录数 |
| filtered | 策略明确过滤的记录数，不是故障丢失 |
| coalesced（新增） | 合入已有汇总的额外查询尝试数，不是被丢弃数 |
| dropped / overflow / oversized | 已知被拒绝、淘汰或明确未存储的记录；overflow、oversized 是原因分类，不重复相加 |
| writeUnknown（新增） | 写请求发出后失去确认，无法判定提交与否的记录数 |
| fallbackSkipped | stdout 因限频/背压未输出的行数，不等同 SQLite 丢失 |

`accepted` 继续表示新接纳的队列记录数，`stored/dropped/writeUnknown` 也按记录计数；`coalesced` 单独按额外尝试计数。一次 emit 合入已有记录时返回该汇总记录 id。各进程状态仅反映自身，不伪装成全系统持久化总账。

写入超时、worker 退出或确认通道失败后，只有能证明未提交的情形才记确定丢失，其余记 writeUnknown。同一条记录不同时记 dropped 和 writeUnknown。先前超时不追溯重新解释。

不自动重发结果未知的批次，不把“重试成功”当作此前未提交的证明。UI 的已有异常提示区分“已丢弃 N 条”和“另有 N 条写入结果未知”；无异常时不增加常驻说明。错误详情仍只用固定代码。

## 实施范围与验证

分两步独立验证，避免一次混入过多变量：

1. 队列内 Drizzle 汇总 + 批次触发调度 + 次数展示。主要归属 `lib/logging/service.ts`，匹配条件就近复用 Drizzle 固定词表；只加必要的展示映射和测试。
2. 写入结果未知分类 + 状态展示。覆盖所有会终止 pending write 的路径，再改计数，不能只替换文案。

验收至少包括：

- 固定输入下，汇总次数精确相等；不同请求、任务、连接、动词不串；业务事件切断合并段；队列/在途/关闭不残留索引。
- 原来的 10,000 个查询尝试 + 100 个任务终态场景：任务终态全部保留，尝试计数可核对，真实丢失和合并分开；另测高基数不可合并与全 error 饱和，仍保持有界。
- 最新双维规则、字段投影、关闭/重新开启、存储 ABORT/FULL/ROLLBACK、stdout 背压、进程退出及丢失确认均有实际管线覆盖，不用假响应替代。
- 原生 201 条业务链路、4 个父子任务保持结果、检查点、真实关联 ID；公开 HTTP/MCP 返回与安全投影不回归。
- 独占负载窗口做交替 A/B：普通业务 + 诊断开启 + 多进程写入；记录吞吐、p50/p95/p99、CPU、RSS、队列峰值、计数、业务响应完整 hash。普通负载要求无 overflow 和 writeUnknown；超载要求有界且计数诚实。相同版本 A/A 用于判断噪声，超出噪声范围的退化必须解释，不以重跑挑绿。
- UI 只验证计数含义与汇总详情，桌面和 390px；临时数据库、进程、端口、浏览器 profile 均留清理凭据。不写用户 50055 的配置或数据。

边界：这是诊断系统，不替代业务数据库里的审计/回执。断电、SIGKILL、磁盘不可写、持续超出消费能力仍可能失去尚未持久化的日志。若未来要求这些情形也持久可靠，再单独评估持久缓冲或外部 Collector；不在本轮加入。
