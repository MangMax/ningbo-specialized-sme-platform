# 文件库入库范围:一份可执行的裁决规则

> 2026-11-17：[平台底座与业务模块边界 ADR](2026-11-17-platform-core-and-business-modules.md)（#874）补充本文：入库范围规则从文件库的通用规则改归名录模块（`sme-roster`），作为它在模块清单里登记的入库策略；下文判据、原因码与处置不变。原文保留。


2026-10-16 · 状态:接受(RL-16,票 #17) · 规则实现 [`lib/file-store-scope.ts`](../../lib/sme-roster/file-store-scope.ts)

**修正** [ADR-来源文件内化为仓库内的文件库](./2026-10-13-source-files-in-repo.md) 的「内化范围」一段(那一版说:经信局的 PDF 与 `.doc` 内化、与 PDF 同名的 `.docx` 不内化)。
**目录规则(`files/<source>/<kind>/<year>/<batch>/<filename>`)与 `source_file` 口径不变** —— 变的只有「哪些文件该进文件库」这条判定。

## 背景

用户 2026-10-16 反馈两件事:①小巨人工作簿的出处写的是**来源目录相对路径**,不在文件库里,
名录行的预览/跳转全断;②文件库里多出**两份重复的 `.doc`** 与**一份 2021 入库培育文件**。

根因不是某一次搬运做错了,而是「该不该入库」这条判定**从来没落成代码** —— 它散在
早期目录说明、项目外 pipeline 的脚本、以及人的记忆里。于是每次搬运都可能再混进来。

## 决定

1. **入库范围只有一个出处**:[`lib/file-store-scope.ts`](../../lib/sme-roster/file-store-scope.ts) 的 `scopeOf()`
   —— 纯函数(相对路径 + 同目录兄弟名 → 入不入库、为什么),可单测。
   回填(`server/utils/stored-files.ts` 的 `backfillStoredFiles`)每次都调用它:
   不在范围内的文件**不进 `stored_file`**,并在回填报告的 `excluded` 里**带原因逐条报出**。
   规则因此是**被执行**的,不只是被写下来的。
2. **判据与处置**:

   | 判据                                     | 处置                                                                     | 原因码           |
   | ---------------------------------------- | ------------------------------------------------------------------------ | ---------------- |
   | 文件名含「入库培育」                     | 不入库 —— 培育对象不构成称号;2021 的称号认定在《甬经信中小〔2022〕145号》 | `nurture`        |
   | `.doc` 且**同目录**有同名 `.docx`        | 不入库 —— 只保留可预览的 `.docx`(台账出处指的就是它)                     | `duplicate-doc`  |
   | `.docx` 且**同目录**有同名 `.pdf`        | 不入库 —— 人工 OCR 产物;PDF 才是权威原件且可内联预览                     | `human-ocr-docx` |
   | 其余落在 `<source>/<kind>/` 规则内的文件 | 入库                                                                     | `in-scope`       |

3. **通知类(申报/复核通知)不入库**,但它的判据是**来源目录段** ——
   库内路径已经丢掉了来源目录,`scopeOf()` 判不了,所以这条只在**来源侧**(pipeline `scanSources()`)执行。
   见下节。
4. **移出是显式动作**:`DELETE /api/files/:id?deleteDisk=1`。回填只保证「不再混进来」,
   不会替人删掉既有的行;已 `removed_at` 的行也不会被回填复活。
5. **出处一律是文件库内相对路径**。来源文件入库后,同一内容的来源标识变了 ⇒
   导入的幂等键(来源标识 + 内容 SHA-256)也变 ⇒ **重导一次**:企业/记录/事件按坐标跳过
   (历史一行不改、一行不增),只把出处的 `source_file` 收敛到新路径。

## 为什么「通知类」不能用文件名判

这份名单里**几乎每份文件都叫「…名单的通知」**(如《关于公布2024年度第一批宁波市"专精特新"
中小企业名单的通知.pdf》)。按文件名排除会把正牌名单一起排掉。来源侧的判据因此是
**目录段**含「通知」(`经信局名单/省专/2023/00第一批通知/`)—— 目录才是「这份文件干什么用的」
的表达。这也解释了为什么这条判定不可能整体搬进库内规则。

## 后果

- 文件库的「应有集合」不再等于磁盘全量,而是**磁盘 ∩ 入库范围**;实测真实库 22 份。
- 「历年汇总」类文件(《经信局公布历年小巨人企业名单.xlsx》)跨第 1–7 批,**没有**单一
  「公布年份/批次」⇒ 按 `lib/file-store-scope.ts`「year/batch 取值」第 4 条省略这两段,
  于是 `category_state` 为 `unset`。那是**年份待核**,不是「不知道它是什么」;
  **不要**为了消掉它硬填一个年份(空值优于错值)。
- ⚠️ **项目外 pipeline 尚未同步**:`pipeline/src/files.ts` 的 `scanSources()` 仍不扫
  `经信局名单/小巨人/`,也仍内化 `.doc`(再由 `convertDocSiblings` 转出 `.docx`)。
  库内规则会把重复件挡在 `stored_file` 之外(回填报 `excluded`),但**磁盘上会重新出现** ——
  需在该目录按本文同步(它不在本仓,故不在 RL-16 的改动范围内)。
