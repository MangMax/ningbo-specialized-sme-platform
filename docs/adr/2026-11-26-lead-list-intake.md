# 线索名单录入、分流与企业补充

状态：接受（2026-11-25 设计讨论，[#909](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/909)）。分流规则见 [#907](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/907)，企业补充契约见 [#908](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/908)。

关联：[平台底座与业务模块边界](2026-11-17-platform-core-and-business-modules.md)、[企业主体共享内核](2026-11-18-enterprise-shared-kernel.md)、[名单分流与线索名单入库](../../.agents/skills/lead-list-ingestion/SKILL.md)。

## 背景

同一系列可从多个渠道收到文件。有些名单每期重发全量，有些名单每年新增一批，例如获奖名单。线索名单的使用流程是查看原件、挑选企业、逐行核对，再按需向企业基础库补充。是否需要管理获奖年份和奖项类别，取决于平台是否经营这项业务。

## 决定

1. **每份名单独立登记，保留历次版本。** 以所属系列、来源渠道、名单类型、获取日期和原文件登记版本。目录按系列排列，系列内按获取日期倒序，同日按版本 ID 倒序。经办人结合日期、渠道和原件判断本次使用哪个版本。替换型和累积型使用同一登记流程。
2. **线索行保存供企业核对使用的原值。** 行保留行号、企业名称及可选的统代、区县和备注。完成补充后保留企业 ID 和核对记录。奖项类别、获奖年份等业务事实需要结构化经营时，进入所属模块以企业 ID 关联的业务子表，原件继续由文件库保存。
3. **以是否需要经营业务状态决定名单毕业。** 纯企业清单统一进入线索池。平台需要以企业为轴心建立业务子表、持续经营该业务状态时，才由对应业务模块承接。正式称号公布名单与工信部平台快照继续按名录模块的既有规则处理。
4. **由 core 提供手动单向补充通道。** 人工或代理先核对并明确提交。线索名单和名录通过 core 公开出口调用 [`applyReviewedEnterpriseSupplement`](../../layers/core/server/utils/enterprise-supplement.ts)，在发起方事务中先锁定相关身份，再按行新建或附着企业并应用显式资料修订。提供来源参数时，core 在各行归属确定后登记来源关联。线索的核对结果回写和幂等判断、名录的来源身份校验与公告来源整理分别由所属模块负责。业务模块通过 core 公开命令写入企业基础库。
5. **所有线索行保存在 `lead_list_row`。** 间接通过版本关联系列与名单类型，行读取和核对以版本为范围。版本原始内容随登记保存，补充只写入企业归属和核对信息。名单毕业时在业务子表中记录业务事实，原线索继续留存。

## 未选择的方案

| 方案 | 取舍 |
| --- | --- |
| 登记时逐份声明追加或替换，或按类型设置默认值并允许录入时覆盖 | 经办人仍须逐行核对并选择本次要用的文件。维护版本关系会增加录入和纠正成本，日期、渠道和原件已可用于判断当前应查哪一份。 |
| 给线索行加业务列或 JSON 扩展 | 补充完成后，线索行的核对职责即告结束。扩展列会让线索模块解释奖项、年份等领域含义，也会分散以后实际经营这些事实的责任。 |
| 按逐年累积或是否有独立字段直接分流 | 来源文件的形态无法说明平台需要经营什么。仅用于走访的历年获奖名单仍属线索，有获奖状态维护需求时才需要业务子表。 |
| 各业务模块各自建挂企业，或让线索调用名录内部实现 | 身份锁、资料写入和来源关联属于共享内核。各自实现会重复维护这些规则，通过名录转调也会让线索依赖另一业务。 |
| 按系列或名单类型物理分表 | 当前规模用版本范围即可查询与回写。版本原始内容固定，业务隔离可由系列、类型与版本关系表达，原件负责保留出处。分表会增加读写和维护路径，毕业时也无需搬迁线索行。 |
| 建立跨版本合并视图 | 逐行核对需要知道同一企业曾在哪些文件出现。行级历史能保留每次出现的版本和出处，足以支持这一判断，合并视图还需规定取哪期的行值。 |

## 后续方向

可在线索挑选界面查询同一企业在同系列各版本中的历史出现记录，保留各次出现的原始行和出处。它属于挑选时的交互增强，待名单使用流程完善后排期。现有登记和补充流程可直接使用版本与原件，当前无需为历史联查改变录入契约。
