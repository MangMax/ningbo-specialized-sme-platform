# 平台业务记录与采集观察分离

> 2026-11-10：[#707 完整退役 ADR](2026-11-10-platform-mixed-table-retirement.md) 提议替代本文长期保留混合 query/relation 运行实体的选择。新提案仍待独立审查，尚未取代已接受的运行契约；本文身份、观察、原字节与决定不变量继续保留。

同一接口返回的同一平台业务编号，代表同一条平台业务记录；采集时间不改变业务身份。原有 `platform_relation` 表达“某次查询的第几行”，它是采集观察，不能同时充当业务身份，否则重复采集会形成重复候选。此决定落实用户在 #243 中确认的口径。

保留现有查询、关系行及其全部引用，增补稳定业务记录、内容版本及观察关联。业务记录以“接口＋非空平台业务编号”唯一；内容相同复用版本，变化保留不同版本；每次采集仍能追到原查询、行号与时间。不同接口分别保留，缺少编号时不按名称或信用代码自动归并。

版本比较以原始业务行的内容为准，忽略 JSON 对象键的排列，保留数组顺序与值类型。旧数据标准列曾漏填，不能把标准列补全、归属确认或采集元数据变化误记为平台内容变更。没有原始行的历史观察不得与有原始行的观察假定等价。

写入与既有归档处于同一事务，由数据库唯一约束保证业务身份、内容版本和观察关联幂等。历史归并通过应用写接口分批、可重入执行，不删除或改指旧证据，不把旧确认自动扩展到内容有变化的版本。业务查询和候选按业务身份组织，原始归档查询继续返回采集历史；业务去重与原始证据保全是两个独立的不变量。

不采用按业务编号直接删除旧 `platform_relation` 的方案：它会损坏已确认对应、差异解释、别名和审计的出处。也不采用仅在页面过滤重复行的方案：外部代理和后续写入仍会把重复观察当成独立业务记录。

## 当前业务记录

申报记录、关联办理和平台认定目录按接口和平台业务编号各保留一个当前结果。列表、筛选选项和详情使用最近一次可核实的采集内容。内容回到此前采集过的值时，以本次采集时间确定当前结果。缺少平台编号或内容无法核实的行仍可从原查询查看。资格、差异和对应关系只能引用该编号的当前采集。同内容复采且业务主体、称号与归属相同，确认及差异依据随当前观测更新，历史保留原坐标。内容或归属变化后，旧引用须重新核实。每个业务编号至多保留最近一次内容不同的核实采集作为回滚备份。同内容重采更新当前采集坐标，不挤占回滚备份。新采集提交时清理更早的观察和无人引用的内容；采集回执只记录当时的查询状态与坐标。具备 API 写权限的维护人员可通过 `DELETE /api/platform/records/{id}/previous` 删除备份。此口径替代本文前述长期留存采集证据的决定。
