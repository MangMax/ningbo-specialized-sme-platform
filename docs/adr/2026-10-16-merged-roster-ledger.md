# 企业总表并入名录台账:一份数据、两种分组、一个差异视图

用户 2026-10-16 反馈「出现了多余的『企业总表』页面,应该将功能和台账页面合并」。合并后**只剩一个入口 `/`**(名录台账),`/roster` 302 重定向到 `/` 并保留查询串。页面内用**分组**切换同一份数据的两种粒度,差异与原因作为第三个视图。

## 为什么是「合并」而不是「二选一」

先核对两页到底是不是在讲同一件事(2026-10-16,真实库 7,352 企业 / 10,501 个企业×称号):

| | `/`(记录台账) | `/roster`(企业总表) |
|---|---|---|
| 一行是什么 | **企业 × 称号**,合并该组合下全部来源 | **企业** |
| 行数 | 10,501 | 7,352 |
| 称号 | 徽章(该组合的一个) | 徽章(该企业全部) |
| 来源 / 事件 | 直接列在行内 | 展开面板里 |
| 筛选 | 称号 / 来源 / 事件 / 年份 / 区县 / 搜索 | 称号 / 属地 / 总表状态 / 搜索 |
| 导出 | `/api/export`(企业×称号) | `/api/roster/export`(企业,xlsx) |
| 差异 | 无 | 差异与原因页签 |

`counts.titlePairs`(10,501)与 `/api/records` 的 `total`(10,501)**是同一个数字** —— `/api/records` 的分组口径本来就是 `count(distinct enterpriseId ‖ '/' ‖ titleCode)`,不是 record 行数。也就是说两页不是两套数据,而是**同一份数据的两种分组**,外加一组只有 `/roster` 有的差异视图。这正是用户说的「多余」。

## 三个方向

用 `oil-ui` 做了三个**信息架构**方向的首屏(沿用项目既有视觉语言与设计变量,只拉骨架,不重做风格),1440×900 各一张:

**D1 单表一企一行(全量收紧)** —— 只留企业粒度,差异做第二个页签。最简;但企业×称号的平铺清单消失,`/stats` 的下钻(见下)数字对不上,`/api/records` 与 `/api/export` 变成孤儿。

**D2 一份数据、两种分组 + 差异** —— 一个筛选条、一个导出按钮,分组控制切 `按企业 / 按企业×称号`,再加 `差异与原因`。零能力损失。

**D3 清单 + 右侧详情(主从)** —— 左侧紧凑企业清单,右侧常驻详情。`oil-ui` 三方向里视觉上最有辨识度的一个;但左侧清单放不下统代/属地,跨企业的横向比较被削掉,窄屏要把右栏降级成抽屉,构建面明显更大。

**选定 D2。** 理由:

1. **不丢能力**。`/stats` 的下钻是 `/?title=`、`?source=`、`?eventType=`、`?district=`、`?year=`(统计页第 92 行的 `drillTo`),点「miit 8,123 条」必须落到**8,123 行**上。只有保留企业×称号粒度,下钻的数字与落到的行才是一回事;D1 会把它变成「有 miit 记录的企业」,用户点 8,123 看到 4,000 家,是静默的口径漂移。
2. **口径变成控件,而不是脚注**。验收要求页面说清「企业数 vs 企业×称号数」。D2 把这两个数字直接做成两个分组,切换即所见 —— 比在描述里写一句更难误读。
3. **D3 的好处已经拿到了**。D3 的卖点是「看详情不用跳页」,而 RL-04 的行内展开已经做到(且行内展开比常驻右栏多留了统代/属地/状态这些横向对比列)。在成本高、窄屏要额外设计的地方再赢一次,不划算。
4. **合入风险最低**。D2 的两张表都已存在,只是收进同一个工具栏下;不需要新写读模型。

## 落地口径

- **一个入口**:`/` = 名录台账。`/roster` 用页面级 `redirect` 302 到 `/` 并**带上原查询串**,深链不断。
- **状态全在 URL**:`view` / `q` / `title` / `district` / `rosterState` / `source` / `eventType` / `year` / `direction` / `status` / `reason` / `page` / `pageSize` / `expand`。刷新、分享、从差异或出处返回都保住视图。
- **筛选透传**:`source` / `eventType` / `year` 在 `按企业` 分组下解释为「该企业存在满足条件的记录 / 事件」。这是对 `lib/roster/enterprise-roster.ts` 的**增量**(三个可选判据),缺省时行为与 RL-04 完全一致。
- **导出跟视图走**:`按企业` → `/api/roster/export`(xlsx,首行写口径);`按企业×称号` → `/api/export`;`差异与原因` 不给导出(RL-04 没有差异导出,也不新增)。

**已考虑但未选:** 把 `/roster` 做成 `/` 的别名路由(两条路径同一页面)——「只有一个入口」就落不了地,侧栏仍会长出第二个导航项;把差异视图并进 `/comparison` 页 —— 那是「公布 vs 平台」的解释工作台,与 `/comparison`(名单比对 + 解释缓存)是两回事,并过去反而制造新的重复。

## 落地时改掉的两处(都在合并页面上)

### 1. 企业行从「六列堆叠」改成「身份两行 + 两列台账事实」

原总表每行 ~110px(称号徽章 `flex-wrap` 堆三行、首次认定再占两行),一屏只放得下 5 家。
合并后 1440 视口下这张表只有 **约 1134px** 可用,而三方各自要的宽度是:企业名 ≈ 300、
三个称号全称徽章 ≈ 336、首次认定+下次复核 ≈ 330 —— 加不出一个不裁字的方案。
上一版硬塞六列的结果是**称号第三个徽章被 `overflow-hidden` 切掉、复核那串被截断**,两处都是真丢信息。

改成:名称 / 统代 / 属地(**身份**)合成一列两行,称号与复核各占一列按需要给足,一行 ~51px。
实测 1134px 内三个徽章与两行复核文字**都不裁**。另外 `TableCell` 的基础类带 `whitespace-nowrap`,
复核单元格必须显式 `whitespace-normal`,否则它既不换行又会被裁。

「当前总表」不再是常态列(295 页里绝大多数行都是它,逐行盖徽章只是噪声),
改成只给**例外**打标:非 `current` 的行在名称旁挂「仅平台引入」。筛选与导出的状态列照旧。

### 2. 差异六态的徽章色收敛到一处

`pages/roster.vue` 与 `components/RosterEnterprisePanel.vue` 原先各有一份
「状态 → 徽章色」级联,两份都把 `not_queried`(未查询)与 `no_record`(无记录)画成同一枚
outline、把 `needs_review`(待核实)与 `query_failed`(查询失败)一律画红 ——
违反契约 §3.2 的「四态必须彼此可区分」(用户反馈过的「失败 ≠ 无记录、未查询 ≠ 无记录」正靠这条守住)。

现在两份级联都删掉,统一取 `lib/labels.ts` 的 `DIFFERENCE_STATUS_VARIANTS`(单一出处):

| 状态 | 变体 | 实际差别 |
|---|---|---|
| 未查询 `not_queried` | `dashed` | 灰字 + **虚线**框 |
| 查询失败 `query_failed` | `destructive` | **红实底** + 白字 |
| 无记录 `no_record` | `outline` | **深字** + 实线框 |
| 待核实 `needs_review` | `quiet` | **灰字** + 实线框 |
| 已确认无差异 `confirmed_no_diff` | `secondary` | **浅灰实底** |
| 已确认原因 `confirmed_reason` | `default` | **主色实底** |

**为什么不是 `solid`。** 第一版给「待核实」挑了 `solid`,理由是它「加粗深框」。实测不成立:
`Badge` 的**基础类本来就带 `font-medium`**,所以字重不是可用通道,`solid` 与 `outline` 的
实际差别只剩**边框浓淡**一处;再叠上调用点当时挂着的 `class="font-normal"`,`twMerge` 把
`solid` 的 `font-medium` 也吃掉了。四个通道(有无底色 / 底色色相 / 字色 / 线型)里,
这样只用到半个,六态实际退化成五态半。换成 `quiet`(灰字)后,「待核实」与「无记录」靠
**字色**分开,六态在这四个通道上两两至少差一处。

`tests/difference-status-variants.test.ts` 就按**实际能看见的通道**钉:
六态各自 `cn(badgeVariants(...))` 出来的签名两两不同;另有一条看源码,禁止调用点再给状态
徽章挂 `font-*` / `text-*`(那会把唯一的字色通道抹平,而「比 class 串」那条用例**照样通过**)。

> 代价一处:`dashed` 在事件徽章那边表示「入库培育」。两处都在同一列的上下文里用、
> 不会并排出现,但这条跨语义复用要在评审时知道。另一条路是给 `Badge` 新增一个警告色变体,
> 那属于改共享组件的视觉语言,不在这张票里。

### 3. 合并暴露的三处「同一个筛选,两种结果」

共用一条筛选条之后,两个读模型原本各自的取舍被摆到了同一个框里。三处都按
「要么两边口径一致,要么这个筛选只归一个视图」处理:

1. **搜索 `q`** —— 合并后台账三个视图共用一个搜索框,框上写着「企业名 / 曾用名 / 统一社会
   信用代码」。但企业总表只认名称 + 已确认曾用名(`/api/roster/enterprises?q=<统代>` 返回 0),
   记录侧只认名称 + 统代(不认曾用名)。**两边都补齐**:企业/差异读模型加统代匹配,
   `lib/query.ts` 的 `buildWhere` 加一条「已确认曾用名」的 EXISTS(只放宽、不收紧,
   不会让既有查询少命中)。三处口径统一成 名称 / 已确认曾用名 / 统代,
   并加了一条交叉用例:同一关键词在两种分组下必须给出同一批企业。
2. **属地 `district`** —— **刻意只归「按企业」**。两个读模型的规则本来不同:企业总表按
   **企业属地**(为空时退回最早记录的属地),记录读模型按**每条记录的属地**。
   实测(2026-10-16,真实库)13 个区县里 **11 个**给出不同的企业集合 —— 同一个 `district`
   值在两个分组下不是同一批人。放进共用筛选条就是「同一个 URL,两种结果」。
   同时把 `setView` 改成按 `LEDGER_VIEW_FILTERS` 清理:原先切到「按企业×称号」时清了
   `rosterState` 却把该视图**根本不发**的 `district` 留在 state 里 —— 地址栏不体现、
   用户清不掉,切回「按企业」时却突然生效。
3. **`/stats` 的下钻** —— `pages/stats.vue` 的每个桶都按**企业 × 称号**计数,而合并后台账
   **默认落在「按企业」**。下钻链接因此补上 `view=title`,否则点「工信部 8,123 条」会落到
   一个「有工信部记录的企业」列表上,数字与落到的行对不上,而且是**静默**的。

另:`/api/export`(按企业×称号的那条导出)补了一行口径 —— 导出的文件常被单独转发,
拿到 xlsx 的人得知道这些行属于多少家**企业**。为此 `ExportRow` 加了 `enterpriseId`
(用 id 去重,不用名字:实测有重名企业)。
