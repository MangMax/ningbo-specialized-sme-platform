# 企业主体升级为平台共享内核

日期为 2026-11-18。决策见 [#886](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/886)，父任务见 [#873](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/873)。本文确定归属和切换约束，实际迁移由实施票交付。

## 背景与决定

企业基础库将同时承接名录、线索名单和后续业务。选择部分升级：core 持有稳定企业 ID、通用资料及来源登记，业务模块保有各自的名单、资格、原始事实与历史。各模块通过 core 的公开命令补充企业，并用企业 ID 引用主体。沿用 Nuxt Layers、业务单库 和现有模块依赖方向。依据见[平台底座与业务模块边界](2026-11-17-platform-core-and-business-modules.md)及[PostgreSQL 19](2026-11-20-postgresql-migration.md)。

## 数据与命令归属

| 归属 | 数据 | 命令 |
| --- | --- | --- |
| core 企业基础库 | 企业 ID、现用名称、可空且有值时唯一的统代、区县代码、乡镇代码、行业代码、在库状态及移出说明。曾用名记录存企业 ID、统代、曾用名、改名年份，年份可空。合并保留旧 ID 指向 | 登记、按指定字段修改资料、维护曾用名、合并、移出及恢复。统代修改与曾用名记录的统代同步在同一事务完成 |
| core 来源登记 | 来源渠道、名单类型、获取日期、所属系列、归属模块及对应业务表标识。用业务来源标识登记，企业与来源通过 ID 关联。有原文件时可关联原件。来源渠道、名单类型用可维护字典 | 登记来源、写入企业与来源关联、查询来源供页面及离线出数。直接新增企业时登记「直接添加」 |
| 名录及其他业务模块 | 名单业务行、正式公告与认定历史、称号状态、领域指标和来源原值 | 各自的录入、修正、移出和领域判断。模块移出只改变自身的业务纳入状态，基础库企业及已登记的历史出处继续保留 |

身份匹配沿用[企业身份 ADR](2026-10-13-uscc-as-identity.md)：有统代时优先按归一化统代匹配，缺统代时按归一化名称精确匹配。多候选交由提交前核对。区县和乡镇分别存代码，行业存 2017 版四位代码，两位大类通过字典取得。行政区划和行业字典由用户提供，随迁移导入。

在库状态描述基础库业务范围。core 的资料与曾用名命令承接对应的既有审计。名录当前维护的迁入、迁出、注销断言仍由名录的主体事实子域写入，保持证明、修订历史及消费语义，见[来源分域](0001-source-domain-boundaries.md)与[名录周期处置](2026-11-16-title-cycle-disposition.md)。共享企业资料的现值与正式来源记录分别保存。既有审计数据及调用方在迁移时逐项核对。

名录等业务模块可对 core 的企业表建外键，也可在自己的查询中关联 core 的企业表。跨业务模块读取走对方的公开出口。原始名单行可以先留存，完成补充并取得企业 ID 后再关联。

## 手动单向补充

1. 名录和线索名单各自完成录入。人工或代理在提交前核对身份、资料和来源，随后明确发起补充，可整批提交。
2. 补充只从业务模块流向基础库。core 按已核对的载荷新增企业、更新显式指定的字段或追加来源。未提供的字段保留现值或在新档中留空。平台执行格式、唯一性和引用校验，企业资料与本次来源关联同事务写入。
3. 模块导入、版本更新及移出本身各自完成。已登记的历史出处继续可查。直接添加表示实际创建方式，历史来源变化按各自事实记录。

## 首版交付

- 企业列表支持基础字段筛选。来源页面展示系列、版本、名单业务数据及原文件。按来源查企业提供 HTTP 或数据库读取路径。企业详情、新 MCP 工具及匹配过程展示留在首版范围之外。
- 纯清单进入线索模块，登记必填项为来源、名单类型、获取日期、所属系列和原文件。获奖等逐年累积且拥有独立业务字段的名单归对应业务模块。分流与录入步骤由技能说明。
- 全景页随首个指标模块验证。组合筛选与排序覆盖完整结果后分页，展示列按本页企业 ID 批量读取。若代表性查询实测出现瓶颈，再由字段所属模块维护对应的窄查询表。数据库选型沿用现有 ADR 的复评条件。

## 迁移与验收草案

1. 盘点现有企业 ID、合并关系、曾用名、审计、事实引用及各名录入口，确认基础库主体归属和现有名录行为的切换边界。
2. 一次性迁移共享主体，保留现有企业 ID、合并指向和历史引用，导入字典。将现有名录企业及其公布出处作为首次明确触发的批量补充，核验来源对应和关联合集。
3. 同一切换中更新调用方并移除被替换的写入口。用升级验证覆盖 ID、引用、别名、历史证据和名录查询，用 HTTP 验证模块录入后须明确补充才进基础库、已核对的字段可以显式更新、模块移出后基础库和历史出处仍可查询。迁移盘点与演练见 [#890](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/890)，一次性切换见 [#891](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/891)。

存量公布名单的来源关联沿用名录台账已有的文件引用。出处路径与在库名单文件精确匹配，且发布渠道一致，即可将对应企业关联到该名单文件。同一家企业在同一份名单中只登记一条来源关联；重跑可补齐此前遗漏的关联并沿用已有来源 ID。文件哈希用于文件内容校验，历史导入回执和出处修订无需重新补录。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| 企业留在名录，通过名录公开出口供其他模块查询 | 改动较小，线索等独立业务会持续依赖称号名录管理共同主体 |
| 主体、来源与指标集中进 core | 单表读取直接，指标口径、年度规则和写入责任会集中到基础库 |
| 仅共享主体和来源登记，业务事实归各模块 | 采用。应用可用同一企业 ID 关联各域，模块保有自己的规则，通过按需查询及必要的派生表支持全景展示 |
