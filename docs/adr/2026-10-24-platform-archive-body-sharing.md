# 平台原档正文共享，采集观察保留

用户在 #269 明确要求真正删除重复正文，而非只合并业务展示。#243 的业务身份、内容版本与采集观察继续保留；同一接口的业务编号相同仍是同一业务，不同接口不合身份，同一内容也不传播观察级确认。正文采用内容寻址存储，原 query/relation/version 只持正文引用；旧 API 继续读取完整原文，旧 ID、出处、决定及其指纹不变。

首版按**完整原文字节**共享，哈希只用来定位，命中后仍比较长度和正文。有效 JSON、非法原文、空字符串、JSON null 与 SQL NULL 分开处理。原 bytes 不同的表示不强行改写；不建设任意 JSON 词法重排配方。canonical 版本正文和原行正文若 bytes 相同引用同一内容，不继续各存完整副本。正文内容不可变，物理引用不代表业务归属或证明资格。

范围为 `platform_relation.raw_fields/source_text`、`platform_business_record_version.canonical_raw_json`、`platform_query.raw_response/collection_evidence`。先落地精确正文池；查询 JSON 中与已登记业务原文**逐字节相同**的完整对象可用有序字节片段引用重组，未匹配部分原样保存。组合根保存逻辑长度和摘要，片段只引用正文叶，不引入递归图或自动 GC。重组必须逐字节等于旧封套，分块读取按偏移取片段，不能每页重组整个大原档；HTML/异常 JSON 保持 opaque，不能解析再伪造原响应。

旧实体表不改名、不以 SQL VIEW/INSTEAD OF trigger 取代；正文引用使用有外键的类型化附表，避免私有引用字段进入既有 `getTableColumns`、DTO 和指纹。兼容读取提供旧字段列表、逻辑 SQL JSON 表达式、精确文本/字节范围接口；保留 metadata-only 车道及原字节预算。所有 reader、指纹、反向引用 SQL、title-scope 触发器和 evidence-revision 接缝适配并验证前，不启用正文清空或引用写入。

正常归档与历史压缩均由应用事务管理，正文写入、引用切换和内联副本清除必须原子完成。历史压缩复用统一 REST/MCP 导入、预检/提交/回执机制，原请求直接提交，不凭空增加另一套 planHash 封套。客户端只指定服务端既有 owner ID，不上传原文或任意池引用；服务端冻结、重读源字节/指纹，漂移冲突拒绝。旧二进制不默认兼容池化后的字段；回滚必须使用支持引用的已验证版本，或先通过受控恢复操作还原内联原文，不能恢复旧 DB 抹掉新业务提交。

不把 audit/provenance、import receipt、平台 job 或导出表的正文迁移搭入首版；其业务内容、历史快照、请求哈希和状态保持。物理重组完成后分别报告各归档桶的原字节、共享字节、引用开销、剩余/不可共享表示及实际页占用。SQLite 空闲页不等于已返还 OS；空间整理另在有一致备份和 writer 独占的 native 卷维护窗口验证，不以字段置空冒充文件缩小。

## 未选择的方案

- 仅把已映射行改指版本正文：可回收大部分旧行副本，但不能统一处理无版本文本、查询原响应及其嵌套副本，容易再次以局部优化宣称清理完成。
- 全库可逆 JSON 表示、审计/回执/job 重构：超过本次平台归档重复正文的范围；先保留实测风险，不为尚未证明的收益扩建通用配方或 GC。
- 删除旧 relation/query：损坏采集事实、来源选择及独立决定，不能作为正文清理手段。
