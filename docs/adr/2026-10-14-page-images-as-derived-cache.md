# 页图(PDF → PNG)是**派生缓存**,落在文件库里但不算「文件库的文件」

`app` 把扫描 PDF **逐页渲染成 PNG**(票 13):PDFium(wasm)出像素,`sharp` 出 PNG,
接到 `POST /api/pdf-pages`。页图落在**源 PDF 旁边**的隐藏目录里:

```
files/<source>/<kind>/<year>/<batch>/.<文件名>.pdf.pages/pNNN.png
files/…/.<文件名>.pdf.pages/.pages.json
```

按 [ADR-tus 上传落在 app](./2026-10-14-tus-uploads-in-app.md) 的前提,「只读」指的是**台账数据
(企业/记录/事件)不被界面修改**;文件写入不受此约束。**凡新增写路径,都单独记 ADR 说明其边界**
(见 [ADR-第一阶段:只读查阅看板](./2026-10-13-readonly-board-first.md)),这份 ADR 说的就是它。

**为什么放文件库(`app/files/`)里,而不是另开一个缓存目录:** 页图是**某一份源文件的**派生结果,
按源文件名派生、放在源文件旁边,人翻开 `files/` 一眼就能看到「这份 PDF 的页图在哪」,也让
`record_evidence.source_file` 的相对路径口径一套到底(渲染端点收的就是那个相对路径)。
放到库里另一个位置,就要再维护一份「源 ↔ 缓存」的映射,而映射本身没有任何新信息。

**写路径的边界(这就是本 ADR 要冻的东西):**

- **只写 `files/**/.*.pages/` 之内**。目标路径由服务端从**源 PDF 的相对路径**派生
  (`lib/pdf-page.ts` 的 `pageDirRelPath`),客户端**只能指一个已存在的 PDF**,不能指目录。
  解析后必须仍在文件库根内(锁根),与文件回吐路由同一把关。
- **不碰源文件、不碰台账**。不写 `stored_file` / `record` 等任何表,也没有迁移 ——
  页号由**文件名** `pNNN.png` 与 `.pages.json` 承载,OCR(票 14)按 `page_no` 回填时若要落表,
  那是票 14 自己的迁移。
- **目录名带前导点**(`.…pdf.pages`)是**契约的一部分**:文件库扫描器
  (`server/utils/stored-files.ts` 的 `scanFileStore`)按「名字以 `.` 开头即跳过」滤掉系统/临时文件,
  于是页图**不会被回填成 `stored_file` 里的「文件」** —— 109 张页图渲染后文件管理页仍是 23 个文件。
  这条规则一动,票 09 的文件管理页立刻被上千张 PNG 淹掉。
- **幂等、可随时重建**:幂等判据是 `.pages.json` 里的**源内容 sha256 + 分辨率 + 每页文件尺寸**,
  四者一致(且没有多余页图)则一个字节都不写;内容/DPI 变了就**原地覆盖**同一批路径。
  因此页图目录**不入库**(`.gitignore` 的 `files/**/.*.pages/`),删掉再渲染即可复原。
- **页图仍然「在库内」给人看**:它的**字节**由既有的文件回吐路由 `/api/files/[...path]` 给出
  (页图清单里的 `url` 就是它),不新开一路文件服务器;`/api/pdf-pages` 只负责「查现状 / 取某页 / 触发渲染」。

**已考虑但未选:**

- **建 `stored_page_image` 表**:那是票 13 原方案的形状,但本次只交后端半边(页面部分与建表留给
  后续票),而页图**只落盘**已足够让 OCR 按页取图。先不建表,免得在一个还没有消费者的形状上定型。
- **放系统缓存目录(如 `~/Library/Caches`)**:文件名里全是中文与书名号,跨目录后「源 ↔ 缓存」
  的对应关系全靠猜;而且备份/清理边界会与文件库脱节。
- **在文件库根下集中放 `.pages/<哈希>/`**:按内容哈希集中存放要维护哈希索引,且人打开 `files/`
  看不到页图属于哪份 PDF。
