# 解析源继续用「代理读正文的 OCR 结果」,但必须有机器校验闸

**决定(票 07):** 公布名单的解析源**继续**是我们自己 OCR 出来的文本(`.docx` 转出件、扫描 PDF 的逐页 `ocr_result`),**不**在导入链路里自建一套权威 OCR 引擎。作为交换,导入前**强制**过两道机器校验闸(`pipeline/src/source-integrity.ts`):**序号连续性**(公布名单段内每个子表必须 `1..N` 无缺号/无重号)与**总数对账**(段内解析行数 == **代理读正文后声明的家数**)。校验不过 ⇒ **非零退出、一行台账都不写**,由人拿 PDF 原图核对(票 05)。

**为什么不是「自建 OCR 当权威源」:** 权威件是扫描 PDF(零文字层,17/17 机器读不出字),要读就得 OCR。自己 OCR 的**精度问题不会消失** —— 我们现在的 `.docx` 本来就是人工/工具 OCR 的产物,它**已经**出过错(整段漏 69 行;4 份文件把序号 9 打成 6),换成自己跑一遍只会换一批错法,还要多背一份外部依赖(政务内网对「连外部 OCR 服务 / 拉模型权重」有硬约束,见 CSP 相关要求)。而**校验闸是确定性的、与 OCR 实现无关的**:不管文本是谁识出来的,缺号/重号/总数不符都能判。

**为什么基准是「代理声明的家数」而不是程序从散文里抠数字:** 正文里的「以上企业共计 1020 家」「等 258 家企业」是**语义判断**,归代理(读正文之后经 `save_parse_result` 写 `stored_file_part.row_count`,`origin='agent'`)。程序**不做**数字/年份/范围推断(NLP 抽取会把「1020 家」这类表述猜错,而且猜错的方式无法穷举)。没有代理声明时,闸**报「无法核对」**而不是伪造一个 N —— 空值优于错误值。

**后果:**
- 校验闸报的是**信号**不是修复:它把「像不像漏了」变成可机检的两条,人仍要看图(票 05)。
- **子表重启是合法的**,判据是源件里**显式的小标题行**(如「二、有效期：2021年12月1日至2024年11月31日」,解析为 `ParsedEntry.listSection`),不是「序号又回到 1」——否则「同一段名单被列了两遍」会被当成合法重启放过。同一附件里并置多段名单(〔2022〕145号 的 198+104+413 = 715)因此照常通过。
- 工信部导出的「序号」列是**源表行号**、按维护批次另起,**不适用**连续性规则(报「不适用」,不静默)。
- 闸**只管两件事**;页码抽检、名称/统代冲突、年份语义覆盖(`mismatches`)仍各自按原口径报告,不因「有 warning」就一律阻断。
- **长期**若改成自建 PDF OCR 作权威源,这道闸**照用** —— 它是「源可能错」的兜底,不是「源是 docx」的补丁。

**已考虑但未选:** ①「同类目里序号必须唯一」—— 已被 145号 的真数据证伪(合法重启会误杀);② 「用节序当页码」—— 已证否(docx 节序可推但非事实,新文件要先验节数==页数);③ 「把 `stored_file_part.has_conflict` 当阻断条件」—— 那是**派生段与代理段行数不一致**的标记,和「源本身漏了行」不是一回事。
