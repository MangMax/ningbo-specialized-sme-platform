# 平台底座与业务模块边界：模块化单体，core 不依赖业务

状态：接受（[#874](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/874)，父 spec [#873](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/873)）；2026-11-17。本文只定架构边界与契约，不授权任何 schema 变更、数据迁移或删列；各步落地按 #873 的子票分别验收。

关联：[保留 SQLite](2026-10-20-retain-sqlite.md)、[来源分域](0001-source-domain-boundaries.md)、[文件库入库范围](2026-10-16-file-store-scope.md)、[平台业务记录身份](2026-10-23-platform-business-record-identity.md)、[tus 上传在 app 内](2026-10-14-tus-uploads-in-app.md)、[术语表“平台”一节](../../GLOSSARY.md#平台)。

## 背景

本仓库定位是覆盖全平台的企业服务系统，但目前只实现了一个业务：优质中小企业 / 专精特新称号名录。开发这一个业务时长出了不少本该全平台共用的能力——文件库、运行日志、后台任务、OCR 与 PDF 预览、密钥配置、应用外壳——它们和名录缠在一起（问题陈述见 #873）：

- `stored_file` 同时放着通用字段（路径、内容哈希、显示名、软删除）和名录专用字段（来源、公告/导出、公布年份/批次、称号、分类状态、解析状态）；入库范围规则也是名录专用的。
- 任务中心的分组、名称和导出唯一索引写死了名录的任务种类。
- 密钥 key 的枚举写死为 `ocrToken`、`miitCookie`。
- 日志只有技术来源维度（http、mcp、task……），没有业务模块维度。
- 侧栏菜单硬编码，顶栏对所有页面显示名录统计，package 名叫名录看板。

接入第二个业务时没有可复用的底座，只能继续往名录里塞，或者复制一份。

## 决定

1. **模块化单体。**仍是一个 Nuxt 应用、一个 SQLite（沿用[保留 SQLite](2026-10-20-retain-sqlite.md)）、单机部署；不拆服务、不拆库、不引入多租户。
2. **两层。**
   - **平台底座（core）**：外壳和导航、文件内核、文档处理（OCR / PDF）、后台任务、运行日志、设置与密钥、鉴权、HTTP/MCP 公共设施，以及模块注册表。
   - **业务模块**：第一个是 `sme-roster`，承接现有全部名录代码；以后的业务各占一个模块。
3. **依赖方向单向：core 不依赖任何业务模块。**core 不 import 业务代码、不写业务特例、不认识具体的任务种类、密钥或文件分类；它只读模块清单。业务模块可以依赖 core。
4. **用 Nuxt 4 Layers 承载。**目录为 `layers/core`、`layers/sme-roster`，以后每个业务一个 layer。物理搬迁放在接缝理顺之后（#873 子票 10、11）；在此之前的子票都在原目录内改造接缝，不先搬文件。

## 模块清单契约

core 提供 `defineAppModule()`，每个模块（包括 core 自己）调用它向注册表提交一份清单。下面的字段是契约本身；具体的 TypeScript 形状由实现子票确定，但不得改变这里的语义和责任划分。

| 字段 | 语义 | 负责方 | 必填 |
|---|---|---|---|
| `id` | 模块唯一标识，kebab-case（如 `sme-roster`）。同时用作**日志 `module` 值、密钥命名空间、新路由前缀**，一经发布不改名 | 模块 | 是 |
| `name` | 显示名（如“优质中小企业”），用于侧栏分组、工作台卡片、任务中心 Tab、设置页分组 | 模块 | 是 |
| `dependsOn` | 依赖的其他模块 id；不允许成环。`core` 隐含为所有模块的依赖，不必声明 | 模块 | 否，缺省为空 |
| `nav` | 侧栏菜单项。业务模块的项进“业务模块”分组，core 的项进“平台管理”分组 | 模块 | 否 |
| `dashboard` | 平台工作台上的卡片（入口与关键数字） | 模块 | 否 |
| `jobKinds` | 本模块拥有的任务种类：kind、显示名、任务中心分组 | 模块 | 否 |
| `logScope` | 本模块日志写入的 `module` 值；取值必须等于 `id` | 模块 | 否，缺省为 `id` |
| `credentials` | 本模块需要的密钥：key、显示名、说明；存储键为 `<id>.<key>` | 模块 | 否 |
| `fileCategories` | 本模块对文件的分类扩展：文件分类、入库策略、文件页筛选项和详情面板插槽 | 模块 | 否 |
| `mcpTools` | 本模块注册的 MCP 工具 | 模块 | 否 |

注册表由 core 负责，规则如下：

- **启动即校验**：模块 id 重复、路由前缀冲突、`dependsOn` 指向不存在的模块或成环、任务种类重复登记，都在应用启动时报错，不留到运行时。
- **兜底**：没有任何模块登记的任务种类仍出现在任务中心“全部”里，以 kind 原值显示；不因未登记而隐藏任务。
- **core 自己也通过注册表登记**，id 为 `core`：平台管理菜单（文件、识别校对、任务、日志、密钥）、`render-pages` 与 `ocr` 任务种类、OCR 密钥都写在 core 的清单里。core 的外壳与业务模块读的是同一份注册表，不另走一条内部捷径。
- `id` 是唯一的命名源。日志 `module`、密钥命名空间和新路由前缀不另设别名，避免三处各叫各的。

## 互通规则

模块之间只能走四条路：

1. **public 出口**（同步读写）：每个模块用一个明确的公开入口导出供他人调用的函数和类型；别的模块只能 import 这个入口。
2. **事件 / Nitro hooks**（异步通知）：发出方只声明发生了什么，不知道也不依赖谁在监听。
3. **界面插槽**：宿主页面开放具名插槽，别的模块往里注册 Tab 或卡片；宿主不 import 注册方。
4. **共享内核**：模块可以引用 core 拥有的实体 ID（如文件 ID、任务 ID），也可以对 core 的表建外键。

**跨模块原子写**由发起方编排：发起方开启一个 SQLite 事务，依次调用各模块 public 出口上的公开命令；各模块仍只写自己的表。这是单库单机才有的便利，不引入分布式事务或补偿机制。

**禁止**（由 CI 边界校验拦截，校验脚本由实现子票提供）：

- 直接 join 或查询别的业务模块的表；
- import 别的模块 public 出口之外的内部实现；
- 在业务模块之间建外键。别的业务模块的实体只存 ID 引用。

## 兼容规则

- **HTTP API 的路径与请求、响应契约，以及 MCP 工具名保持不变。**智能体客户端、技能和脚本依赖这些接口，模块化不能让它们跟着改。
- **页面地址不作兼容承诺。**本应用是内部工具，页面链接不对外分发；页面因工作台调整等原因换了地址，直接改站内链接即可，不为旧地址做重定向。
- **新模块**的页面路由与 API 使用 `/<module>/...` 前缀，MCP 工具使用 `<module>_` 前缀（`<module>` 即清单 `id`，MCP 工具名中的连字符按工具命名规则转写）。已有名录路由与工具名属于存量，不追加前缀。
- **密钥** key 改为 `<module>.<key>`，读取时兼容老 key，已保存的密钥不需要重新填写；不开放任意 key 写入，只接受清单里登记过的 key。

## 迁移节奏

所有拆分按 expand → 影子对照 → 切换 → contract 推进，每一步可以单独上线、单独回滚：

1. **expand**：新增结构与读写路径，旧结构保持可用；需要时双写并回填。
2. **影子对照**：新旧读取对同一输入并行运行，产出差异报告；零差异（或差异全部经批准单列）才能进入下一步。
3. **切换**：逐个消费者切到新读取，旧读取仍可退回。
4. **contract**：删除旧列、旧接口或旧代码。**删列和删接口需要单独授权**，并且要有可读回的回滚记录；本 ADR 不授权任何删除。

文件分类是第一个按此节奏推进的拆分：`stored_file` 上的 source、kind、year、batch、title_code、category_state、parse_state 迁到名录模块的分类表（暂定 `roster_file_classification`，以 file_id 为主键），`stored_file_part`、解析审计和入库范围规则归名录；以 `/api/files` 系列与文件相关 MCP 工具的响应保持一致作为影子对照判据。日志库增加 `module` 维度（取值为模块 id 或 `core`），与技术来源 `source` 正交。任务 `job` 表外壳不变，kind 的登记、显示名和分组改由清单提供，按 kind 建的唯一索引归所属模块。

## Nuxt Layers 的两个坑

1. **自动导入全局合并。**各 layer 的 `components/`、`composables/`、`utils/` 会合并进同一个自动导入命名空间，任何 layer 都能直接用到别的 layer 的组件，绕过 public 出口。因此**业务 layer 的组件和 composable 必须带模块前缀**（如 `Roster*`），让误用在命名上就显眼；跨模块使用仍以 public 出口和界面插槽为准，由 CI 边界校验兜底。
2. **同名文件按优先级静默覆盖。**多个 layer 存在同路径的页面、API 路由或资源时，Nuxt 按 layer 优先级取一个，不报错也不告警。因此**新路由一律带 `/<module>/` 前缀**，从路径上排除撞名；注册表启动时也校验路由前缀冲突。

## 未选择的方案

- **微服务**：单机部署、单一维护者，跨进程调用、部署编排和分布式事务的成本远大于收益；模块边界在单体内用目录、注册表和 CI 校验就能守住。
- **多库**（每个模块一个 SQLite）：会失去跨模块单事务，跨模块原子写只能靠补偿；与[保留 SQLite](2026-10-20-retain-sqlite.md)的单库前提也不一致。日志库独立是既有的例外，不推广。
- **万能业务表**（一张带 type/JSON 的表承载所有业务记录）：每个消费者都要解释全部字段，失去类型、索引和约束，与[来源分域](0001-source-domain-boundaries.md)的“各来源拥有自己的字段与查询”相冲突。
- **通用规则引擎**（含通用依赖图）：现阶段只有一个业务，抽象没有第二个实例检验，只会把名录规则换个地方写死。规则留在各模块代码里，入库策略等由模块以函数形式提供。
- **日志并入审计**：运行日志是可清理的运维数据，业务审计是证据，二者保留期和清理语义不同；日志继续留在独立库，清日志不清审计（与[来源分域](0001-source-domain-boundaries.md)一致）。
- **提前做多租户、多用户身份与权限**：当前 token 是单机防护，没有多租户需求；另行立项，不在本次调整里预埋。

## 待定事项

- **企业主体归属**：企业主体是留在 `sme-roster` 内，还是升级为 core 共享内核供后续模块引用，尚未决定，由 [#886](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/886) 讨论并另立 ADR。决定之前，新模块不得直接 join 名录的企业表；需要时通过 `sme-roster` 的 public 出口读取，并只保存企业 ID 引用。

## 后果

- 接入或下线一个业务模块不需要改 core；如果接入第二个模块时仍需改 core，应修正本契约，而不是给 core 加业务特例（#873 子票 14 负责验证）。
- 看目录即可判断一段代码的归属；跨模块耦合只能通过 public 出口、事件、插槽和共享内核发生，并可被 CI 发现。
- 本文不推翻既有 ADR 的任何不变量：来源身份与观察分离、文件内容身份、入库范围判据、日志与审计分离、单 SQLite 均继续适用。[文件库入库范围](2026-10-16-file-store-scope.md)的判据不变，但从文件库的通用规则改为名录模块的入库策略。
