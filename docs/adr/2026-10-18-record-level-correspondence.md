# 拟议：以有类型的记录级对应连接正式事件与平台证据

## 背景与选择

当前企业×称号的历史公布集合和当前导出集合直接求差，不能表达“2021 年认定已与平台当年行相符，但 2025 年另一次更新退回”。现有查询/关系证据虽保留原行，差异原因引用某行仍不能证明它属于哪一个正式事件。选择**正式事件、平台流程行、平台已认定行、当前导出行四种独立节点，加有类型、角色、状态和审计的具体行对应边**；后续流程允许只关联企业×称号而没有正式事件。事件/流程可直接以 `current_snapshot_context` 连接指定版本的导出原行，不要求存在已认定接口行；这只提供可反查的快照出处，不授予导出行历史结论权威。导出与已认定行也可建立候选边，只有同范围、同时点和同版本资格可证时才产生现状一致性结论；无导出行只记录查询覆盖与条件，不造正面行。对应候选和已确认分开，原始事实不因解除边而改变。

考虑过（1）继续按企业×称号只取最新状态并附整个查询，（2）把平台行直接塞入 `record_evidence` 当正式出处，（3）让每条后续申请都强制挂到最近事件。它们分别会消除历史批次、混淆权威与来源、以及把新流程误写成旧复核结果。记录级多对多模型要求额外的候选与审计成本，但保住原行、时间、类型和证据角色；软件仍不自动推断业务原因。

## 后果与审批边界

同批次流程若已确认对应正式获批事件，而获批后原状态仍待审核/退回，记录为来源陈述的 `historical_conflict`，按事件去重；不能因为已认定行缺席改报“缺对应”，也不据此自动判平台未更新等业务原因。新对应需复用统一名录鉴权、原子预检/提交、幂等与公开读回；旧 `difference_reason` 和旧对比保留为兼容/历史读模型，迁移先只读预览，用户明确确认后再通过 API 执行。#34 的事件与正式出处精确更正是独立操作，更正后相关边须重核。本文不冻结物理表名或路由最终拼写，不授权实现、数据写入或创建子票；这些需在 Spec 独立评审后逐切片决定。
