# 差异调查与判断

同一企业跨文件、跨称号由一名代理负责。软件采集查询并保留关系；代理先判断记录是否不一致，再判断原因与后续措施。负责人及交接见[多代理编排](orchestration.md)。用户指定 Magpie + DeepSeek Open Design 时，业务判断使用该组合；代码、部署和写入代理执行已确认的决定，不替代判断代理。

## 单个企业的处理步骤

整批任务先按[负载编排](orchestration.md)完成任务分组和资源预算，再由每片负责人执行以下步骤；疑难项与普通项分队列，保持相同业务证据标准。

1. 固定主体、称号和本批范围，记录真实导出版本/日期、查询范围/时间，以及每个相关正式事件的源文件、附件、名单序号。完整保留正式行和原始名称。名单对比还须固定本地实际部署的资格规则、判断时点及双方快照；规则改变后重算本地有效集合、双向差集与处理建议，不在旧名单上仅追加标签。
2. 复用已有查询、完整归档、确认别名及已核验来源。区分正式认定/复核结果与申请、公示草案、维护记录。文件入库仍按 `workflow.md` 做逐页核验；后续判断不必重复已完成核验。名称地名变化或属地冲突按“地名变化与迁移查证”主动搜索；用户明确限定已有证据或三接口时，遵守该限制，后续明确授权网络搜索则按新范围处理。
3. 仅在授权范围内，通过应用 REST/MCP 补缺失证据。`queryList` 是申报，`businessList` 是关联，`queryBusList` 是已认定企业。先看能力，再按[平台查询说明](platform-query.md)执行。保留全部关系、原时间与页码；不读 Cookie、不直调平台。完整零行与失败/部分完成/未解析分别记录。
4. 按下节对应正式事件与平台记录。先读任务详情中的全部历史行和公布出处，必要时查看当前公开对应证明与记录级对比契约，复用已确认对应；候选对应仍需独立确认，读取/对比不会自动确立对应或业务原因。
5. 先确认是否真正存在差异，再按判断表分类。历史一致性与后续流程状态分别保留；主体、称号、年度批次、业务类型有歧义时具体说明，不能只取最新一行代替。
6. 写清观察事实、对应记录、判断及出处；业务交付按下文“业务情况表与问题闭环”区分主表和底稿。核心字段待核先定位缺口所在层，只列真正缺失的事实。`other` 必须是已经确立的具体原因，不能装入尚未完成的调查。记录主体、公布依据、属地或对应关系未明确时，面向用户统一列为“待人工审查”，并写具体问题。
7. 仅在用户写入授权范围内交接已确认结论。只要求报告时，完成报告即停止。单一写入者核对在线契约，任务判断按下节 current/token 覆盖写回，其他独立入库协议各自预检、提交和读回。名称/别名、原因与正式事件分别有依据、分别写入。采集输出或脚本字段映射不能冒充代理决定。

## 对应具体记录

比较单位是一次正式事件及其对应的平台业务记录，不能把企业历次称号历史直接与最新导出成员集合比较。

- 先确认主体和称号，辨明原认定年/批次、认定或复核结果、结论年度。按有依据的业务单号/认定标识、称号、年度批次和流程类型对应。提交时间、原认定年和复核结论年是不同事实。
- 查看全部申报及关联记录，不只看 `queryBusList` 或最新时间。认定、复核失败、重新申报、更新可分别是真实事实，须完整保留；不同称号互不抵消。
- 每条对应明确标“已确立”“候选”或“无依据”，并带实际行引用。查询成功不代表返回的每一行都能证明该事件；元数据缺失留空，不猜填年度批次等价关系。
- 导出表代表导出时间及查询范围内的已认定企业列表，须与后续接口查询的时间、范围一起记录。先核对原始行、称号、条件和版本，再解释不一致；导出不是独立于认定接口、另有一套业务历史的权威来源。
- 按 Excel 表头找信用代码，不能假设三张表列位相同。有的工作表错误声明范围为 `A1`，须确保全表读取，例如 openpyxl 只读模式重置工作表范围。按已确认代码匹配同称号并核实有证据的名称；另一称号的命中不解决本称号对比。保留实际 Excel 行号，不记录无关联系人字段。

## 对应后的业务判断

| 记录事实 | 判断与边界 |
|---|---|
| 历史正式认定与平台记录对应一致，后续待审/退回/复核流程能对应，未发现相反正式结果。 | **无差异**。历史认定与后续流程原文分别保留；当前导出缺失或没有某年新公布，不独自构成差异，也不证明称号到期。 |
| 正式认定/复核结果已公布，对应同称号、年度批次的平台流程尚未体现。 | **平台未更新**。写明实际滞后的流程，不要求查明平台内部机制。历史事件已由历史通过记录对应时，不能自动归入此类。 |
| 对应正式结果与较新的认定/流程均存在，记录的导出尚未体现，且用户确认按未更新处理。 | 按已确认口径记 **平台未更新**。保留流程原文、认定行、快照/查询时间，不编造同步机制，不将所有接口/导出不一致一律如此分类；若原始表实际已有同称号行，应纠正“导出缺失”的错误观察。 |
| 所要求的接口、称号和分页范围全部完成且均为零行。 | **无记录**。注明整户零还是仅同称号零。保留正式历史；零行不证明注销、迁移或失效。失败及未完成范围属于查询缺口。 |
| 同一主体的旧名/现名或迁移起点/终点已有证据。 | 按证据判断 **更名、迁入或迁出**。复用已确认依据，不因旧报告漏列就要求重搜公开来源。迁移日期、原称号/年度/批次等补充字段未知时留空，不阻塞已确立的事实。 |
| 平台复核通过，但检查过的来源中未找到对应正式复核公布。 | 先检查是否已确立迁入或迁出；已确立时按迁移分类，复核出处缺口单独保留。迁移未确立时列 **待人工审查**，写复核年度批次、已查新旧名及缺少的来源。不能仅因旧认定已公布就判无差异；仅更名已确认也不能消除复核公布缺口。 |
| 平台认定存在，对应正式来源缺失，或主体、属地、记录对应确有冲突。 | **待人工审查**：写明确切缺失或冲突。旧报告所谓“事实不足”“数据匹配需核对”统一用此顶层分类，解释中保留具体子类。 |

流程状态本身不等于差异原因。待审、退回、不通过记录先放回对应历史中解释。复核失败与后续重报分别保留；不只凭退回、当前无行或无新公布推断撤销、失效。

## 地名变化与迁移查证

名称从“宁波”变为“嘉兴”等外地名、从“上海”等外地名变为“宁波/浙江”，以及企业现名仍带外地名但认定属地为宁波，都应主动检查迁出、迁入和更名。名称中的地名是查证入口；“浙江”覆盖多个城市，不能单独证明在宁波或已迁出宁波。

1. **固定同一主体**：先按已确认信用代码串联公布名、接口各次名称、现名与曾用名。比较同一企业的旧址、当前登记地址、总部地址、认定属地及各自时间，分别标注来源；总部、通讯地址和登记地址不互相冒充。主体链待核时保留候选，不按名称相似合并。
   搜索前先遍历输入中三个接口的全部关系，按接口列出行数、不同名称、城市/区县和证据行 ID；同时查看规范字段及原始字段中的 `qymc`、`szsmc`、`szqmc`。后面的认定行与原始字段也属于必读范围，不能仅读开头或只看省份。用脚本投影/去重可减少输入体积，但保留原行引用，不用脚本替代业务判断。结论交付前核对是否存在尚未解释的新名或异地记录。
2. **主动网络搜索**：复用已有依据后，并行搜索“完整旧名 曾用名”“完整现名 地址/总部”“旧名 现名”“信用代码”，只补沿革和方向缺口。以百度等搜索引擎聚合结果为主要入口；结果偏题时使用引号限定完整名称、精确代码或换引擎，不能一次未命中就转待核。留存查询词、工具/引擎、网址、摘要原文、查询时间及可识别的来源时间；只在确实使用百度时称百度结果。
3. **分清决定的依据**：用户明确确认同一主体的现名、曾用名和迁移方向时，保存用户决定及时间，复用已确认代码，进入合法 API 的预检与写入；无需再把已确认事实退回待核。用户仅提供候选名称或问“是否迁入”时，仍完成查证。接口要求的证据字段按真实来源填写，不伪造平台行或公开网址。 接收人工最终表时，按[接收人工最终表](#接收人工最终表)逐个主张辨明确认和回写范围。
4. **相对宁波分类**：同一主体从宁波迁往外地为 **外迁**（`moved_out` / `mark_moved_out`）；从外地迁入宁波为 **迁入**（`moved_in` / `record_moved_in`）；只确立名称变化、未确立迁移为 **更名**（`renamed` / `update_current_name`）。迁入/迁出伴随更名时，以迁移为本次主差异原因，在说明及曾用名中同时保存更名事实，不因原因码单值而丢弃沿革。迁移仍未确立且属地冲突不能解释时，列待人工审查并写缺口。
5. **分开企业处置与事件缺口**：已确认外迁足以说明为何宁波当前名单缺失时，主原因标外迁，不因宁波复核公布未找到而继续把整项仅列为无法判断。原复核流程、公布出处缺口及历史称号完整保留，缺失事件不补造；迁入同理。仅有更名、没有迁移事实时，复核公布缺口仍按判断表处理。
6. **交接与读回**：分别列旧名、确认现名、已确认代码、方向、起终点及证据或用户决定、原因与措施、待核补充项。应用现名更新后旧名作为已确认曾用名可搜索，正式名单及接口原始名称不改。迁入原城市、原称号、原年份/批次及迁移日期只填有依据的值；当前称号不能代填原称号，查询/维护时间不能代填搬迁时间。证据不足的补充字段留空，不阻塞已确认迁移。写入前核对当前名称/别名及原因 API 契约，单一写入者预检、提交并分别读回，任务差异核对 expected 后覆盖当前值并读回操作记录；接口不支持的动作明确报告。

### 聚合结果如何支持闭合

- 按主张判断证据是否足够：同码记录支持主体对应，旧地与现地记录支持方向。搜索摘要可以与归档接口、历史导出及其他可追溯搜索结果共同构成证据链；无需把官网正文、工商变更原页或搬迁公告设为统一必需项。搜索平台生成的无出处回答或孤立摘要仍不能独立确认迁移。
- 判断信息时间、明确程度、主体一致性及相互印证，不对官网、工商页、搜索摘要机械排序；各来源都可能滞后。摘要没有来源日期就如实记未知，查询时间不冒充事实发生时间。多个网页转载同一材料只算一条来源。
- 同一已确认主体旧来源明确在外地、当前认定接口明确为宁波区县，并有现名/现地公开搜索结果印证时，可确认迁入方向。旧导出仍保留原地址可解释为历史快照，不自动覆盖现地。准确登记变更日期和街道地址未知可留空。
- 同一主体历史在宁波，当前可追溯资料明确登记地在外地时，可结合其他身份/属地证据确认外迁；宁波总部、办公或招聘仍存在不自动构成反证。分别记录工商主体迁移与业务据点保留，不要求证明所有业务整体搬走。只出现外地工厂或基地则不能代替主体迁移。
- 只有主体、地址用途、来源时间或迁移方向存在真实矛盾时才定向读原页或追加搜索；反爬本身不是业务冲突。仅缺非必需补充字段时直接交付已确立结论，不把“补日期/原页”写成整个案例的待核条件。
- 搜索未命中只说明本次未找到，不能据此判“无迁移”。先覆盖接口中全部名称，再用去地域的独特字号加“曾用名/现名/注册地址/控股”等扩展，避免一直重复旧全称或误追同字号子公司。新主体候选仍须回到同码身份链核对，注册资本变化本身不证明不同主体。
- 工具路由到百科、招聘或其他窄源而未命中时，切换一次可用的通用网页搜索引擎；首次发现缺密钥的引擎不再在同批重复尝试。搜索路径与证据不足分开报告。信用代码前缀不证明现地，也不能据其未变化推断“尚未办理迁址/换号”。

## 业务情况表与问题闭环

### 交付结构与完成状态

沿用用户已整理的表头及分组；没有模板时，主表简洁表达“原状态—相关情况—当前判断—下一步处理”，只保留办理所需的企业标识、时间和批次。不把接口行ID、内部枚举、证据路径或排查日志塞进主表；用稳定企业标识、称号和具体记录关联技术底稿，底稿保留完整来源与查询范围。

用户要求“详细历史”时，逐项展示本称号已核验的全部认定、复核事件，并注明已知缺口；当前有效判定依据另行表达，不能用最新一次事件或跨称号派生依据替代本称号历史。

展示归类不能反向成为事实或写回原因。例如用户将“区县已审”“已退回待审核”归入“申报未通过”时，原状态与“继续审核”“重新提交”分别保留，不能统一写成“终审不通过”，也不能以处理建议代替已经执行的动作。

分别交接调查是否完成、系统更正是否读回、外部办理是否待办。已明确“需平台同步认定结果”可以是完成调查后的业务待办；“有效期异常需与平台确认”仍有明确问题，不能因没有“待核”字样就称已解决。

### 待核字段的定位与分流

沿现有依据定位首个分歧：正式源件及附件页段、接口全部关系、保存原值、业务字段映射、资格读模型、导出单元格。检查与该字段相关的链路，不为每个空值重新做全库采集或无限搜索；遵守用户限定的证据范围。

- 源件已给出而保存缺失：交接已有入库或事实更正流程。
- 原值已保存而业务字段、读模型或导出遗漏：交接程序修复，并保留可复现原值及预期。
- 已知值错误或证据冲突：按实际错误层选择正式更正或业务裁决，不能用只补未知值的接口覆盖已知值。
- 来源确实未提供：写明确切缺项、已查范围、下一步及阻塞状态；不能凭删去待核文字或猜填完成交付。

记录实际修正的是源数据、文件描述、正式事实、投影还是显示，以及下游哪些已验证。保存分段描述不等于正式记录已经同步；已有更正入口、授权及读回要求继续沿本技能执行。

### 接收人工最终表

逐个主张辨明字段含义，区分表中观察、用户明确确认、来源核验和授权回写范围。复合备注中确认一个字段，不扩展到同格其他字段或整行事实。

例如备注“2023年；从杭州市迁入”，先确认年份表达什么及其依据；用户只确认“来自杭州”时，不能连带认定2023为迁入年或声称该年已回写。记录用户处理决定与事实确认的区别，既有已确认依据直接复用，不无故要求用户重复确认。

### 修正后的重新交付

获得写入授权后，按对应公开协议提交并读回，再重新生成本地有效名单、双向差集及受影响处理建议。明确本轮实际使用的规则、判断时点和导出版本；以实际结果验收，不沿用上一版固定企业数。

按稳定标识对账新增、移除、保留及身份变化，逐项区分源数据修正、程序修复、规则调整和人工排除，并关联具体依据或明确标为未解释。成员减少不能自动计入已解决；名称变化不误算新增。运行[成员与原因对账](report-reconciliation.md)，按显式主体键及口径生成机器回执和可读报告；缺说明或身份异常须处理或明确留待核，不能把工具退出0当成系统更正或外部办理完成。

旧工作簿保留为原口径快照。涉及额外有效依据或资格范围变化时，使用当前已确认规则，不把规则派生有效冒充正式认定年份、批次或来源；调查报告完成与未执行的系统修正、外部办理分别说明。

交付前按本次约定运行[工作簿版式检查](workbook-layout-check.md)，覆盖明确的工作表、业务范围及字体/冻结/筛选等属性；修订前后用[原生值与修改边界检查](workbook-value-check.md)证明业务值、类型、成员及应保持属性没有越界变化。约定与回执保存在Git外；失败或未覆盖范围须修正后重跑或明确说明，不能省略异常后宣称已验收。具体字体、尺寸和表结构取自本次要求，不固化为全局偏好。

历史内容或版式修改后，抽查最终文件各表最长、多行及复杂换行内容的实际可读性；原生值读回正确不等于内容完整可读。发现阅读限制时，说明读取完整历史的方式，保留用户指定版式，不擅自调整行高或删减历史。

## 用户明确确认的“待审核”分类

只有在对应记录后，用户明确确认某批范围和解释时，才把“待审核”作为差异分类。“历史终审通过＋最新 `sblx=更新` / `cszt=待审核`＋当前导出缺失”只描述流程，不能自动变成判因规则。按用户确认的记录对比口径，历史与后续流程一致时判无差异，待审核保留为流程状态。口径变化不自动改写旧的授权批次；先逐案预览影响并保留审计。

明确按待审核处理时，检查全部同称号相反终审，包括复核不通过后又更新的记录。业务类型不同，不能只按时间覆盖：“更新/待审核”不能反转“复核/终审不通过”。先保留完整过程交代理/用户判断，不自动纳入待审核写入批次。

明确确认后记录 `reasonCode=pending_review`、`status=confirmed_reason`、`measureCode=follow_review`（保留正式公布历史并跟进审核）。这里 confirmed 表示分类已确认，不表示正在审核的申请已通过；它与 `needs_review`（待核实）、复核失败、称号到期、平台未更新分别处理。用户已确认的分类，不因未知内部根因而撤回；该授权分支无需额外正式文件/PDF/网络证明。未知时间或字段为 null。

保留正式事件、原流程号/类型/提交时间/状态、三个接口引用和用户决定；任务判断按下节读取 current/token、覆盖写回并读回操作记录。

[合成判断示例](adjudication-examples.md)覆盖无差异、待审核、失败流程和来源缺口。不得擅自把授权批次扩大到其他企业或状态。

## 全量采集与判断队列

全量刷新前，协调者核对部署版本、创建一致备份，并通过应用查询 API 取得实际企业清单。在 Git 外用稳定企业 ID、已确认代码建立清单。采集范围可含当前无差异企业；是否进入原因调查队列另行决定。

选择全表分页或逐企批量前先看能力，不假设允许空筛选。保留每个 batchId/itemId、实际条件、称号/页范围、原始时间、分段和未完成位置。按 `platform-query.md` 限制只补缺口。单一写入者对支持的证据逐批预检、提交、读回，之后才能称该行已入库。

采集后以 difference-snapshot 任务快照及其任务队列领取坐标，按下节详情读取和覆盖写回。完整保留三接口分页、分段、失败与未完成范围；同企业跨称号一名负责人，复用证据。

### 旧数据只读背景

`GET /api/roster/record-comparison` / `list_record_comparison` 仅用于查阅旧事件对应和历史 scoped 观察，不能作为新任务队列或写回入口。旧解释、回执及版本审计只读，不执行追加解释、旧解释复核或预检提交旧决定流程。新任务使用冻结快照和当前判断，判断表与迁移查证仍适用。

`queryBusList` 可作为独立 `recognized_list` 通过统一预检/提交转存，保留每个原批次分段、时间及分页/行对应。核对读回查询/行 ID 后才算入库完成。来源、条件、时间或结束证明缺失继续待处理，不能改标 `business_list` / `apply_list`。见[归档转存](../../../../docs/platform-recognized-evidence.md)。采集、证据入库、代理判断分别统计完成量和阻塞。

每位调查者交接企业 ID、称号、已对应事件/流程引用、原文状态、结论/措施建议、未知字段及核验状态。用户报告使用中文业务分类和原文，不用内部枚举解释业务。企业数与称号/事件项数分开，说明重叠，分组边界保持稳定。待人工审查统一分类并列具体问题，不拆散成含糊私有标签。只有协调者提交结论。指定 Harness/模型无法启动时如实报告，不把未执行描述为已审，也不悄悄更换运行组合。

## 按接口解释字段

- `cszt` 的“已退回待审核”“撤回”“终审不通过”等描述该申请/流程，不独自证明正式称号丧失、工商注销或导出差异原因。
- 先对应记录，再用判断表。正式公布确立称号事件；查询证明接口当时返回什么。当前缺失或流程待审都不能独自决定整段称号历史。
- 省对省、市对市、区县对区县。`szsfmc=浙江省` 不能证明企业不在宁波；信用代码前缀或名称中城市不等于当前属地。
- 导出注册地址、通讯地址、认定接口行政属地是不同事实，也可能处于不同时间。逐个标来源，不能用旧注册地址覆盖当前属地。
- 相对宁波判断迁入/迁出，须有起点与终点证据。同一已确认主体旧来源在杭州、现来源在宁波/北仑时，应查证迁入，而非迁出。原城市/称号/年度/批次能确认则保留，未知留空；查询提交时间不是搬迁日期。
- 多个 `qymc` 是更名查证线索。只有代理/用户确认的身份链可授权确认别名或合并；即使身份待核，也保留全部原始名称。

## 默认待核、代理判断与覆盖写回

1. 从企业列表读取待核企业。需要重算时调用 `POST /api/roster/differences/refresh`，可选 `enterpriseIds`；通过 GET 同路径读取逐称号的比较结果。该结果复用现有比较逻辑，不等于代理已确认的结论。
2. 按用户指定范围读取三张业务表、正式事件及企业详情，使用上面的判断表逐案调查。能证明无差异时提交 `confirmed_no_diff`；能确定原因时提交 `confirmed_reason`。无法判断则保留待核并说明已查范围与缺口。
3. 写回使用现有差异原因公开 API/MCP 的预检、提交和读回协议，以当前 OpenAPI / tools/list 为准。判断由代理和人工执行，不绑定采集任务、不创建独立候选队列。新采集记录不自动确认原因或无差异。

历史结论和来源保留。业务输入变化后刷新回待核；相同业务输入再次采集或刷新，已有判断保持。

## 主体事实写回与多事实解释

迁入、迁出、注销/登记状态确立后，按[主体事实公开协议](enterprise-facts.md)分别预检、保存、读回和确认来源断言，独立事实继续走其协议；差异依据按既有差异原因协议保存。独立主体事实固定引用版本；改写差异原因不撤销独立事实，更正/撤回事实不改写历史决定引用。更名继续走企业资料/曾用名接口。
