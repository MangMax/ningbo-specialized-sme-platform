# 来源文件库(File Store)

经信局公布文件与工信部导出表存放在应用运行目录 `files/`,按**来源 / 类别 / 年份 / 批次**分层。
这是运行时业务数据，不属于 GitHub 代码交接包；应用仓库只保留本说明。源文件、页图、上传件须通过受控备份或应用上传在环境间交接，不应提交到 Git。
文件库由 app 与 pipeline **共同消费**(边界见
[ADR:来源文件内化为仓库内的文件库](../docs/adr/2026-10-13-source-files-in-repo.md))。

- app 的 `record_evidence.source_file` 存**相对本目录**(`files/`)的路径(如 `jxj/announcement/2024/1/…pdf`),据此解析并预览/打开。
- pipeline 的 `build:files` 脚本按同一规则把源文件从数据根拷入本目录,幂等可重跑。

## 目录规则

```
files/<source>/<kind>/<year>/<batch>/<filename>
```

| 段         | 取值                      | 来源                                                                     |
| ---------- | ------------------------- | ------------------------------------------------------------------------ |
| `source`   | `jxj` / `miit`            | `jxj`=经信局,`miit`=工信部                                               |
| `kind`     | `announcement` / `export` | `announcement`=公布文件(经信局 PDF/`.doc`),`export`=导出表(工信部 Excel) |
| `year`     | 四位年份                  | 公布文件本身(见下「year/batch 取值」)                                    |
| `batch`    | 阿拉伯数字(1、2…)         | 同上;无批次(导出表、年份区间)时**省略该段**                             |
| `filename` | 原文件名(含文号)          | 保留原样,便于人读与回溯                                                 |

示例:

```
files/jxj/announcement/2024/1/甬经信中小〔2024〕72号关于公布2024年度第一批宁波市“专精特新” 中小企业名单的通知.pdf
files/miit/export/创新型中小企业导出Excel.xlsx
```

## 入库范围(唯一出处)

**哪些文件该进文件库,由 [`lib/file-store-scope.ts`](../lib/file-store-scope.ts) 的 `scopeOf()` 裁决。**
那是一段**可执行的纯函数**,回填(`server/utils/stored-files.ts` 的 `backfillStoredFiles`)每次都会
调用它:不在范围内的文件**不进 `stored_file`**,并在回填报告(`GET /api/files` 的 `backfill`)的
`excluded` 里**带原因逐条报出**。规则不是散文:下面这张表就是 `scopeOf()` 的判据,
改一处就必须改另一处(决策记录见 [ADR-文件库入库范围](../docs/adr/2026-10-16-file-store-scope.md))。

| 判据(库内相对路径 / 文件名)                    | 处置                                                                                                                                                                                                                 | 原因码            |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| 文件名含「**入库培育**」                        | **不入库**。入库培育是**培育对象**、不构成称号;2021 的称号认定在《甬经信中小〔2022〕145号》里(该文件附件含「有效期 2021年6月1日起」那一段),故排除《〔2021〕160号 入库培育名单》不会丢任何称号记录                     | `nurture`         |
| `.doc` 且**同目录**有同名 `.docx`               | **不入库**(重复件)。只保留**可预览的** `.docx` —— 台账的 `record_evidence.source_file` 指的就是它;浏览器打不开旧版二进制 `.doc`                                                                                     | `duplicate-doc`   |
| `.docx` 且**同目录**有同名 `.pdf`               | **不入库**。那是**人工 OCR 产物**;`.pdf` 才是权威原件且可内联预览                                                                                                                                                    | `human-ocr-docx`  |
| 其余落在 `<source>/<kind>/` 规则内的文件        | **入库**                                                                                                                                                                                                             | `in-scope`        |

来源侧(项目外 `pipeline/` 的 `scanSources()`)与上表**同口径**:扫 `经信局名单/{省专,创新型,小巨人}`
与 `工信部名单/*.xlsx`;**目录段**含「通知」的一律不收(申报/复核通知不是名单);`.docx` 不内化。
⚠️ 现状与这条口径**尚有一处不一致**,详见下文「内化范围(来源侧)」—— 那是项目外的目录。

> **「通知类文件」这一条只在来源侧判得了。** 库内路径(`jxj/announcement/<year>/<batch>/…`)已经
> 丢掉了来源目录,`scopeOf()` 无从判断 —— 而且判据必须是**目录段**,不能看文件名:这份名单里
> 几乎每份文件都叫「…名单的通知」。所以通知件要在**收录那一步**挡住,别指望库内规则兜。

> **移出已入库的文件要显式做。** 回填只保证「不再混进来」,**不会**替你删掉既有的行 ——
> 用 `DELETE /api/files/:id?deleteDisk=1`(见下文「移出」)。已 `removed_at` 的行回填不会复活。

### 「历年汇总」类文件:没有年份/批次段是正常的

《经信局公布历年小巨人企业名单》(`.xlsx`)是**跨第 1–7 批**的汇总工作簿,**没有**单一的
「公布年份 / 批次」⇒ 按下面「year/batch 取值」第 4 条**省略这两段**:

```
files/jxj/announcement/经信局公布历年小巨人企业名单.xlsx
```

这正是 app 自己的落位规则对 `(source=jxj, kind=announcement, 无年、无批次)` 给出的路径
(`server/utils/tus.ts` 的 `landingSegments`)—— 所以它可以经**公开上传接口**原样落进去,
不需要为它开特例。它的 `category_state` 是 `unset`,意思是**年份待核**,不是「不知道它是什么」;
**不要**为了消掉这个 `unset` 硬填一个年份(空值优于错值)。


### year / batch 取值

**优先取目录结构**(公布文件所在路径),回退文件名,再回退省略批次:

1. **year**:路径中 `省专/<year>/` 或 `创新型/<year>/` 的年份段(公布年份)。
2. **batch**:批次目录名前缀的数字(`01第一批公布` → `1`,`03第二批公布` → `2`)。前缀数字只用于排序,批次号由目录名里的「第 N 批」解析(`parseBatch`);解析不出时取前缀数字。
3. 目录给不出时,回退到**文件名**里解析(`parseBatch`)。
4. 仍解析不出 → **省略**对应段(如年份区间 `2021-2022`、纯通知类文件无批次)。

> 注:年份取**目录**(公布年份)而非文件名,因文件名里出现的年份有时是**复核的原始认定年份**(如 2024 年发布的「2021 年度第一批复核」),取文件名会串年份。目录结构本身就是按公布年份组织的。

### 命名约定

- 文件名**原样保留**(含文号 `甬经信中小〔YYYY〕N号`),不改写、不规范化。
- 同一文件名出现在多个来源目录、且按规则落到**同一路径**时,追加来源子目录段消歧(见下「冲突消歧」),保证源文件一个不丢。

### 冲突消歧

极少数情况下,两份来源文件(经信局的 `省专` 与 `创新型`)按规则落到**同一路径**——
实测 1 例:`甬经信中小〔2023〕121号…通知.pdf` 在 `省专/2023/02第二批通知` 与 `创新型/2023/03第二批通知` 各一份,同年同批次同名。
此时在 `<batch>` 之后追加来源子目录段(`省专` / `创新型`)各落一份:

```
files/jxj/announcement/2023/2/省专/甬经信中小〔2023〕121号…通知.pdf
files/jxj/announcement/2023/2/创新型/甬经信中小〔2023〕121号…通知.pdf
```

只有真正撞名的文件才加这一层;其余文件仍严格遵循 `<source>/<kind>/<year>/<batch>/<filename>`。

### 去重(幂等)

脚本以**内容 SHA-256** 判重:目标已存在**同名同内容**文件则跳过。因此重复运行不产生重复文件,
打印「落库 0 个,跳过 39 个」。

## 内化范围(来源侧)

> 这是**来源目录**侧的收录口径(项目外 `pipeline/` 的 `build:files` 干的活)。落到 `files/` 里之后
> 该怎么裁,见上文「入库范围」—— 两边同口径,但**判据不同**(来源侧看得见来源目录,库内看不见)。

**应有口径**(与「入库范围」一致):

- 经信局:`经信局名单/{省专,创新型}` 下的 **`.pdf` 与 `.doc`**,**目录段**含「通知」的一律不收。
- 经信局:`经信局名单/小巨人/经信局公布历年小巨人企业名单.xlsx`(历年汇总工作簿,RL-16 起入库)。
- 工信部:`工信部名单/*.xlsx`(三份导出)。
- **不内化**与 PDF 同名的 **`.docx`** —— 那是用户手工 OCR 的产物,后续由「从 PDF 自动提取」替代。
- **不内化**与 `.docx` 同名的 `.doc`(重复件;可预览的那份足够)。

**实测现状(`pipeline/src/files.ts` 的 `scanSources()`,项目外)与上面差两条**:

1. 它**不扫** `经信局名单/小巨人/` —— 所以那份工作簿**不能**靠 `build:files` 落进文件库,
   要靠 app 的上传接口(见下文「生成方式」的例外一条);
2. 它仍内化 `.doc`(再由 `convertDocSiblings` 转出 `.docx`)—— 于是它下次跑会把已移出的
   `.doc` **又拷回磁盘**。库内规则会把重复件挡在 `stored_file` 之外(回填报 `excluded`),
   但**磁盘上会重新出现**。

这两条需要按上面的口径同步到 `pipeline/`。它在**本仓之外**,不在 RL-16 的改动范围内
(见 [AGENTS.md](../AGENTS.md) 的交接约束与 [ADR-文件库入库范围](../docs/adr/2026-10-16-file-store-scope.md))。

## 二进制处理

仓库根的 `.gitattributes` 把 `*.pdf`、`*.doc*`、`*.xlsx` 标注为**二进制**(`-text -diff`),避免 diff 噪音。
PDF 与 `.xlsx` 浏览器可内联预览。

### `.doc` 的转出件(供预览)

旧版二进制的 `.doc` 浏览器端**打不开**,所以 `build:files` 会顺手用 LibreOffice 转出一份
**同名 `.docx`** 放在旁边。台账 `record_evidence.source_file` 指的是这份**可预览的 `.docx`**。

**RL-16 起,原 `.doc` 不再留在文件库里**(判据 `duplicate-doc`,见上文「入库范围」):
它和 `.docx` 是同一份东西的两种封装,用户口径是「重复 DOC/DOCX 只保留可预览的 DOCX」。
所以台账里**不会**再出现指向 `.doc` 的出处 —— 实测两份 `.doc` 的被记录引用数都是 **0**,
移出它们一行历史都没动(见 `tests/stored-file.test.ts` 对真实文件库的核对)。

- 转出的 `.docx` 由脚本生成,**不要手工放**;源目录里若已有同名 `.docx`(人工 OCR 产物),
  脚本会跳过、不覆盖它。
- 需要 LibreOffice(`soffice`,可用 `SOFFICE_PATH` 指定);找不到就跳过并打印一行提示,
  `.doc` 仍照常落库(只是不能预览),不会让建库失败。
- **不要改成转 PDF**:本机 headless LibreOffice 缺中文字体,转 PDF 会把正文整篇丢成空白
  (退出码仍是 0)。详见 `pipeline/src/files.ts` 的 `convertDocSiblings`。
- **验收口径是「可预览、内容可读」,不是「渲染正确」**:这两份 `.doc` 本身是 **OCR 产物**
  (文件元数据里 `Title/Subject = OCR_RTF`),转出件忠实保留原文字,也忠实保留了 OCR 的残留
  (78 号那份末尾有 `-819157429504490085750570` 这类串号)。转换解决的是「能不能打开」,
  不解决 OCR 质量;串号清理是另一件事。

## 页图(PDF → PNG,票 13)

扫描 PDF **没有文字层**,机器读不出 —— 识别(OCR)之前得先把每一页**渲染成像素**。
页图落在**源 PDF 旁边**的隐藏目录里:

```
files/<source>/<kind>/<year>/<batch>/.<文件名>.pages/pNNN.png
files/<source>/<kind>/<year>/<batch>/.<文件名>.pages/.pages.json
```

例:

```
files/jxj/announcement/2024/1/.甬经信中小〔2024〕72号….pdf.pages/p001.png
files/jxj/announcement/2024/1/.甬经信中小〔2024〕72号….pdf.pages/p003.png
```

| 段           | 取值                                                            |
| ------------ | --------------------------------------------------------------- |
| 目录         | `.` + **源文件名(含 `.pdf` 后缀)** + `.pages`                   |
| 页图文件名   | `pNNN.png`,**三位补零、从 `p001` 起连续**;页号就是文件名的数字 |
| 清单         | `.pages.json` —— 源 sha256 / 分辨率 / 每页尺寸,幂等的判据       |

- **目录名为什么带前导点**:文件库的扫描器(`server/utils/stored-files.ts` 的
  `scanFileStore`)按「名字以 `.` 开头即跳过」滤掉系统/临时文件。页图是**派生数据**,
  不是文件库里的「文件」—— 不隐藏的话,回填会把上千张 `pNNN.png` 当成独立的源文件塞进
  `stored_file`,文件管理页立刻被页图淹掉。前导点让**既有规则**替我们挡住。
- **为什么按源文件名派生**(而不是按内容哈希集中存放):人翻开 `files/` 一眼就能看到
  「这份 PDF 的页图在哪」,且与 `record_evidence.source_file` 的相对路径口径一致;
  同一目录下的多份 PDF(如 `2024/1/` 里有 143 号、58 号、72 号)各归各的,不会撞。
  目录名里保留 `.pdf` 后缀,是为了不跟同名的 `.doc` 撞进同一个目录。
- **页图基本不进库**:`files/**/.*.pages/` 已在 `.gitignore` 里(一份 97 页的 PDF 出 42 MB PNG),
  需要时重渲染即可。

### 分辨率

默认 **300 DPI**(A4 输出约 2480×3508 px,兼顾扫描件小字与上传体积；可选择 400 DPI)。页图先将透明区域合到白底,
再转灰度、按 1–99 百分位归一并轻度锐化(sigma 0.6);不做二值化,避免丢掉浅色字。可按文件覆盖,
上限 600 DPI。页图里写了 DPI 标注(PNG 的 pHYs),下游不必猜。

### 幂等

判据是 `.pages.json` 里的 **源内容 sha256 + 分辨率 + 每页文件的尺寸**:三者都与上次一致、
且目录里没有多余页图时,**一个字节都不写**(重跑只花几毫秒)。内容变了或换了 DPI 才重渲染,
且**原地覆盖**同一批 `pNNN.png` —— 目录不随重跑膨胀;源页数变少时多余的页图会被清掉。

### 由接口生成,**不要手工放**

```bash
# 渲染整份 PDF(幂等):
curl -X POST localhost:3000/api/pdf-pages -H 'content-type: application/json' \
  -d '{"file":"jxj/announcement/2024/1/甬经信中小〔2024〕72号….pdf"}'

# 查现状(页数 / 已渲染页数 / 每页尺寸与预览 URL):
curl 'localhost:3000/api/pdf-pages?file=jxj/announcement/2024/1/甬经信中小〔2024〕72号….pdf'

# 取某一页的像素:
curl -o p003.png 'localhost:3000/api/pdf-pages?file=…&page=3'
```

渲染是 **PDFium(wasm)** 出像素 + **sharp** 出 PNG(选型理由见 `server/utils/pdf-pages.ts`);
路由与规则见 `lib/pdf-page.ts` / `server/api/pdf-pages.{get,post}.ts`。页面的**字节**仍由
`/api/files/[...path]` 回吐(清单里的 `url` 就是它),不另开一路文件服务器。

## 生成方式

由 pipeline 的脚本生成,**不要手工放入**:

```bash
cd pipeline
vp run build:files --root "…/20261013"        # 默认写入 ../app/files
vp run build:files --root "…/20261013" --dry-run   # 只算不写
```

`--files <path>`(或 `FILES_ROOT`)可改目标根。

> **例外:经公开上传接口进来的文件。** 不在 pipeline 收录范围内、但确实该入库的来源文件
> (目前是《经信局公布历年小巨人企业名单.xlsx》)**经 app 自己的写路径进来**:
> `POST /api/uploads`(tus,tus 按 `landingSegments` 算出落位路径)→
> `POST /api/files/register`(登记进 `stored_file`)。这样落位、判重、幂等都由**生产用的那套规则**
> 决定,不需要为单个文件开特例(RL-16)。
