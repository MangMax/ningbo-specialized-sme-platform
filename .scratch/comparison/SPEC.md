# 两侧名录比对(应纳未纳 / 应出未出)— 设计规格

> 追踪器:`.scratch/comparison/issues/`。词汇以 [GLOSSARY.md](../../GLOSSARY.md) 为准;数据模型见 [docs/data-model.md](../../docs/data-model.md);上游留白见 [roster-board 票 12](../roster-board/issues/12-reconciliation.md)。
> 本文件只描述**为什么 / 做什么 / 怎么算**,不写实现细节。

## 问题陈述

经办人手上是两张网:**经信局公布文件**(宁波市认定并公布的「专精特新中小企业」「创新型中小企业」名册)与**工信部三份导出名单**(全国口径,含小巨人)。同一家企业,两个来源各录一条;两条本该大体重合,但**差集才是要办的事**:

- 有些企业在经信局名册里(**已经获得/被培育**),却不在工信部对应名单里 —— 需要跟进是否该报工信部(**应纳未纳**)。
- 反过来的**应出未出**,也大多有明确业务原因(企业已迁出宁波、已注销、厂区在宁波但注册地在外省)。

口径已经散落在两份人工比对的 Excel(`20261013/市专比对.xlsx`、`创新型比对.xlsx`)里 —— **各自 2 张 sheet、只列了差异条目**,没有系统化、没有覆盖小巨人、口径凭手工判断。本期要把它**做成看板里的一个模块**:同一套口径、可复核、可下钻、可导出、可逐年复用。

**为什么现在能做**(之前挂起的原因已消失):经信局侧的**身份归一化**已完成 —— 统代已从人工整理版回填(无统代 335 → 3),同一法人按统代归并(123 家)。两个来源现在能**对上身份**了,差集才有意义;在此之前比对只会把写法差异误报成差异。

## 口径(已定 — 依据用户 2026-10 人工比对)

口径以**用户的两份比对 Excel 为准**,已用当前库逐步反算复现(见「口径复算」)。三条:

1. **核心判据 = 统一社会信用代码**:某企业在该称号的**一侧有记录、另一侧无可匹配统代**,即为一条差异。**同一法人不同写法**(如 `有限公司`↔`股份有限公司`)由经信局侧的统代归一化归并处理,不靠名称模糊匹配,也**不做名称回退** —— 名称回退会误报。
2. **不限认定年份窗口、不排除 `入库培育`(nurture)**:「在经信局名册」= 该企业在**经信局该称号**下有**任意**记录(含 2021 入库培育、含复核),不限年份。**复现依据**:市专 337 / 创新型 543,与用户 Excel 抽样完全一致;若排除 nurture-only 会掉到 122,对不上。
3. **不限当前城市为宁波**:漂移企业(如注册地已迁到嘉兴、杭州)照常算差异,并在差异条目上**标注** `当前城市 ≠ 宁波市` / `已注销`,让人一眼看出多半是这类原因。用户 Excel 的差异条目里就含 `嘉兴市`、`杭州市` 的行。

**为什么是「企业级」而非「记录级」**:比对单位是**企业 × 称号** —— 用户 Excel 的 first sheet 首列即「企业名称」,且「在经信局有记录」由该企业的**任意**经信局记录满足(含 nurture)。故归一化维度 = `(enterprise_id, title_code)`。

**小巨人无经信局来源**(GLOSSARY):经信局不发布小巨人,故小巨人**恒无差异**,不出现比对 tab。

## 口径复算(设计期用当前库验证,供实现者照抄断言)

| 称号 | 应纳未纳(=在经信局、不在工信部) | 应出未出(=在工信部、不在经信局) |
|---|---|---|
| 专精特新中小企业 `specialized_sme` | **337** | **13** |
| 创新型中小企业 `innovative_sme` | **543** | **28** |
| 专精特新“小巨人” `little_giant` | 0(经信局无此来源) | 0 |

用户 Excel 的抽样行均在上述集合内(如市专「应纳未纳」的 `宁波建工广天构件`、`宁波公牛数码`,创新型「应出未出」的 `派恩杰半导体`、`宁波邵金塑料`)。

### ⚠️ 一个必须写进模块说明的**假阳性**案例

`宁波市鄞州区规划设计院` 会**同时**出现在两个方向:

- **应出未出**:工信部侧统代 `9133021257053651XQ`;
- **应纳未纳**:经信局侧统代 `12330227732092318Q`(见 `市专比对.xlsx` 第 14 行)。

同一个法人,两个来源**各写了一个不同的统代**。按「统代为核心判据」,它就是一条双向差异 —— 这**不是本模块的 bug,而是源数据的统代错**,模块的价值正是把它**暴露**出来。它同时会命中质量侧的 `name_ambiguous`。

> 处理:与既有类别「两来源统代冲突」(pipeline 侧,按名称归并同一法人)同一类问题,**交给 pipeline 在导入侧归并**,不在比对模块里特判。见「后续 / 不在本期」。

## 用户故事

1. 作为经办人,我想按称号看到**应纳未纳**清单,以便跟进「经信局有名、工信部没有」的企业。
2. 作为经办人,我想按称号看到**应出未出**清单,以便核对「工信部有名、经信局没公布」的企业。
3. 作为经办人,我想在每条差异上看到**命中依据**(统代 / 名称)与**另一侧的状态**(另一侧无记录),以便判断是不是写法或统代问题。
4. 作为经办人,我想一眼看到差异条目里哪些是**外市注册 / 已注销**,以便先排除这些再谈「谁漏了」。
5. 作为经办人,我想把某一方向的差异**导出**,以便交给同事或归档。
6. 作为经办人,我想把企业**人工标注**为「已核实、无需处理」(`curated`),以便下次重算不再冒出来。
7. 作为经办人,我想看到**两来源统代冲突**(如鄞州区规划设计院)这类可疑条目被列出,以便回源核对。
8. 作为维护者,我想口径**集中在一处纯函数**里,以便逐年重算结果稳定、可测。

## 数学定义(按企业 × 称号)

设某称号 `T`:

- `J(T)` = 在经信局该称号下有**任意记录**的企业集合(含 nurture / 复核,不限年份)。
- `M(T)` = 在工信部该称号下有记录的企业集合。
- `key(e)` = `e.uscc_norm`,缺失则 null。

则:

- **应纳未纳** `missing_in_miit` = `{ e ∈ J(T) : key(e) ∉ keys(M(T)) }`(含 `key(e) = null` 的,即两侧都无统代可比对时按「另一侧无匹配」计入)。
- **应出未出** `extra_in_miit` = `{ e ∈ M(T) : key(e) ∉ keys(J(T)) }`。
- **两边统代不同 → 两边各计一条**(见假阳性案例)。

`direction` 取值沿用既有 schema 枚举:`missing_in_miit`(应纳未纳)/ `extra_in_miit`(应出未出)。

## 实现决策

- **模块位置**:新增页面 `/comparison`(侧栏入口),与 `/`、`/stats`、`/quality` 平级。**不并入 `/quality`** —— 质量页是导入后的原始数据体检,比对是跨来源**分析**,关注的问题与受众不同。
- **计算在 app 侧**:这是**只读分析**,现有 `lib/query.ts` 已有全部所需记录;新增一个纯函数 `getComparison(db, opts)` 即可,**不改 schema、不改 pipeline、不做物化**。`reconciliation_result` 表**保持不用**(schema 里已有,本期不写它;理由见下)。
- **为什么不用 `reconciliation_result` 物化**:7,425 家企业下,比对是**毫秒级的分组差集**,每次请求现算即可;物化会引入「何时重算」的一致性问题(用户已明确否决快照类概念),收益为零。
- **`curated` 不做物化存储,落 JSON**:人工确认标注写入 `data/reconciliation-curated.json`(企业统代 × 称号 × 方向 → 备注),由 `getComparison` 读取并置 `curated=true`。app 现有写盘先例是 tus 上传目录;**这是一个显式的、有限的写口子**,只允许标注/取消标注,不允许改记录。
  > 若用户更倾向「二期再上标注、一期纯只读」,把票 04 拆出去即可,票 01–03 不依赖它。
- **命中依据**:记 `evidence = { matchedBy, otherSideUscc, currentCity, regStatus? }`。本期全部按统代命中或未命中;`matchedBy` 保留扩展位但不做名称回退。
- **UI 只用 shadcn-vue 官方组件**:Tabs(按称号)/ Table / Badge / Button / 复用现有 `StatTile`、`DrillChip`、`TitleBadge`、`ExportButton`。沿用 `useQuery` + `placeholderData: (previous) => previous`(避免切 tab 闪回)。

## 接口契约(概要)

- `GET /api/comparison?title=&direction=&page=&pageSize=` → `{ rows, total, counts }`。
  - `title` 缺省遍历三称号;`little_giant` 恒空。
  - `direction` 缺省两方向都返回;可取 `missing_in_miit` / `extra_in_miit`。
  - `counts` 返回按称号 × 方向的分组计数(**必须先于 rows 返回**,用于 tab 徽标与两侧入口;不要让前端自己数当前页)。
  - 行内含:企业名 / 统代 / 区县 / 称号 / 方向 / `curated` / `evidence`。
- `PATCH /api/comparison/curated` → 标注/取消标注(票 04)。
- 导出复用现有导出通道(票 03),列 = 企业名称 / 统代 / 区县 / 称号 / 方向 / 当前城市 / 登记状态 / 备注。

## 测试决策

- **只测外部行为**:给定 fixture 库(直接 drizzle 插桩,不经导入管道),断言两个方向的**成员集合**与**计数**。
- **口径回归测试(关键)**:构造两条已知企业(一条双侧有、一条单侧有),断言差集方向正确;并断言 **nurture-only 记录仍使企业计入 `J(T)`**(锁死「不排除 nurture」这条口径)。
- **假阳性回归**:构造「两来源同法人不同统代」的 fixture,断言它**同时**出现在两个方向(这是设计意图,不是 bug)。
- **不改 schema**:`tests/db.test.ts` 不新增迁移断言。
- 无 UI 单测,页面以真实库人工验收。

## 范围之外

- **不做名称模糊匹配**(会误报,如 `宁波耐达技术股份有限公司` 同时命中应出未出 —— 属另一类问题,交 pipeline 人名/名称归并)。
- **不做跨称号的「梯度一致性」校验**(如「创新型在册、专精特新却没登记」)—— 另一类分析,本期不做。
- **不改 pipeline、不改 schema、不做物化**;两来源统代冲突的归并交 pipeline 导入侧。
- **不做小巨人比对**(经信局无来源)。

## 后续 / 不在本期

- pipeline 侧:把 `宁波市鄞州区规划设计院` 这类**两来源统代冲突**按名称归并为同一法人(与既有「同一法人归并」同机制),归并后这条双向假阳性自动消失。
- 名称层面的近名核对(单字之差、跨来源别名),并入既有 `spztx-data-cleaning` 技能,不在比对模块。
