# 11 — 代理只从「已上传文件」解析(不再扫数据根)

**What to build:** pipeline 的**输入源**从「数据根目录扫描」改为「app 的文件库 + `stored_file` 表」。

**Blocked by:** **17**(按段建模)

**Status:** implemented(2026-10-14,分支 `feat/agent-reads-uploads`,待主代理复核;按 README 规则本票**不需要** oil-ui 验收 —— 界面零变化)

## 现状与要改什么

- 现在:`src/inputs.ts · readInputs(root, filesDir)` 用 `discoverAnnouncements(root, subdir)` **扫数据根**(`经信局名单/**`、`工信部名单/**`)。
- 改成:从 **`app/files/`**(+ `stored_file` 表给的元数据)枚举,`.docx/.doc` 走 parser,`.xlsx` 走 miit parser。
- **`--root` 扫描降级为「离线校验用」**(`check:jxj` 仍可用),**导入路径不再依赖数据根**。

## 关键设计点

- **按「段」取元数据,不按文件取**:一个文件可含**多年份、多事件**(见票 17)。从 `stored_file_part` 读每一段的 `(title_code, event_kind, year, batch)`,写进对应的 `record_event`;**文件级的 `year`/`batch` 是「公布批次」,不能拿来当记录的年份**(192号 就是「公布于 2024 第2批,另含 2021 第2批复核」)。
- **分类从表里读,不从路径猜**:`source/kind` 取 `stored_file`;**未分类的(`unset`)跳过并报出**,不猜(交票 12)。
- pipeline **要读 app 的库** —— 这加深了耦合。已在 `src/db.ts` 复用 app 的库结构;此处再读 `stored_file` 表即可,**不新增第二个连接**。
- `.doc` 仍依赖本机 LibreOffice(既有约束),找不到时**逐文件报错、不整批失败**。

## 输入契约(现在的样子)

1. 从 `stored_file`(未移出库)枚举;`source` / `kind` / `title_code` / `category_state` **读表**,不从路径猜。
2. `.docx` / `.doc` → 公布文件解析器;`.xlsx` → 工信部导出解析器。
3. 同一份文档的 `.doc` 与转出的 `.docx` **只解析一次**(`.docx` 优先),另一份进「跳过」清单 —— **每一行都有交代**。
4. 记录的 `(称号, 事件, 年份, 批次)` **按段**定:段坐标先读**文档正文**;文档没写年份(段标题里没有年份)才用 `stored_file_part` 里**文件声明的段**补。**`stored_file.year` / `batch` 在导入路径上一次都没被读过**(文件级那两个是「公布批次」)。
   > 为什么不是「声明段无条件覆盖文档」:声明段本身就是从 `record_evidence` 回填的**派生**表,让它反过来覆盖它的来源会把「文档明确写了 2021」压成 `null` —— 丢已知值,与「空值优于错误值」相悖。两者不一致时**报出来**。
5. 跳过:`category_state='unset'`、称号定不了、PDF、非 `.docx/.doc/.xlsx`。失败:`.doc` 缺 LibreOffice 等 —— **逐文件**,不整批失败。
6. 称号来源:`stored_file.title_code` → 声明段 → (工信部导出)列位表兜底;三处都没有 → **跳过并报出**,不猜(交票 12)。

## 已知缺口

1. **票面「新 PDF → 库里有新记录」按字面不成立。** 文件库有意**不内化**人工 OCR 的 `.docx`(见 `files/README.md`「内化范围」),存的公布文件是**没有文字层的扫描 PDF**;目前没有 PDF 解析通路,新 PDF 只会进「跳过」清单。等价验收用 `.docx` 做(那也是 SPEC 里 OCR 三通路之一:用户把官网识别好的结果上传)。**补齐要等票 14。**
2. **在生产库上重跑会另立主体。** 新路径的输入面比旧路径小(上面 11411 条差额),而管线的身份索引是**从当期输入**建的 —— 输入面一缩小,原本靠「公布文件 + 工信部」双来源互证的名称就少了证据,于是**安全阀按设计拒绝归并、另立主体并打 `uscc_conflict`**。实测在生产库副本上重跑:+75 主体(其中 **59 个 `uscc_conflict`**)/ +115 事件;演示库里 +77/+117(比前者多的 2 条正是那份新文件)。
   - 这**不是票 11 新引入的机制**:旧路径用同样缩小的输入面(`--title specialized_sme`)重跑,一样多出 **+198 主体 / +988 事件**。是**既有性质**被新默认触发了。
   - 安全阀本身**没被动过**:全程 `merged 0` —— 没有发生任何单来源归并,拿不准时是「另立主体 + 标记」。
   - 建议:先跑 **票 14** 补齐输入面再对生产库重跑;或在**新库**重建。**这是本票最该先处理的一条。**
3. **`MIIT_BY_FILENAME` 按文件名取列位与称号。** 导出表的列位只有定义里有(`MIIT_FILES`),称号与列位同源,只能一起取 —— 这是**列位表**,不是「从路径猜分类」;但确实是文件名依赖。换成表里的 `title_code` 要等票 12 回写。
4. **`stored_file_part` 只读、不写**(按任务简报的明确要求)。它是从 `record_evidence` 回填的**派生**表(票 17),票 11 写了 evidence 之后,下次回填会自己长出段来。代价:一份**新**文件在**第一次**解析时没有声明段,年份只能靠文档正文 —— 文档里没有年份时该段年份为 `null`(不猜)。
5. **2021 那份 `入库培育` 名单不再被文件名排除。** 旧路径靠文件名里的「入库培育」挡掉它;新路径里它是 PDF(跳过),所以**今天结果一样**。但票 14 一旦能读它,它会变成一条 `nurture` 段 —— 那时要不要收,需要一个决定(现无自动排除)。
