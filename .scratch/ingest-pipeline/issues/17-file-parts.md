# 17 — 文件含**多段**:年份 / 批次 / 事件按「段」建模

**What to build:** 更正票 09 的单值模型 —— 文件级只保留「**公布年份/批次**」(目录给的),**文件里含哪些段**另立表;页面把年份/批次/事件显示为**多个**。

**Blocked by:** 09(已合入)

**Status:** done（已随文件管理/多段模型合入）；用户 2026-10-14 指出，这是票 11 的前置。

## 为什么(实测,不是设想)

一份公布文件常含多年份、多事件;**19 份经信局文件里 7 份是多段**,3 份工信部导出**全部**多段:

| 文件 | 段 |
|---|---|
| 省专 2022(145号) | 认定 2021(301)+ 认定 2022(413) |
| 省专 2024 第二批(192号) | 认定 2024/2(389,附件1)+ 复核 2021/2(67,附件2) |
| 省专 2025 第二批(30号) | 认定 2025/2(423)+ 复核 2025(260) |
| 创新型 2025 第二批(165号) | 认定 2025/2(427)+ 复核 2025(394) |
| 创新型 2026 第一批(65号) | 认定 2026/1(382)+ 复核 2023/1(75) |

⇒ **单个 `year`/`batch` 会把 192号 的「复核 2021/2」整个丢掉** —— 而票 11 要靠它把 `(事件, 年份, 批次)` 写进 `record_event`,**不修则票 11 必错**。

## 要做的

1. **新表 `stored_file_part`**:`file_id` / `title_code` / `event_kind`(award/review/maintain/nurture)/ `year` / `batch` / `attachment` / `row_count`。
2. **文件级改语义**:`stored_file` 的 `year`/`batch` **改名为「公布年份/批次」**(目录给的、单值),**别删** —— 它是「这份文件是哪一批公布的」,有意义且在列表里可排序。
3. **回填**:优先从 `record_evidence` 按 `source_file` 分组聚合得到(实测 21 份有引用、可直接用);`.doc` 那 2 份与 miit 导出留待票 11 在解析时写。
4. **页面**:年份/批次列显示**多个**(如 `2021、2022`);行可**展开**看段明细(称号 / 事件 / 年份 / 批次 / 附件 / 行数)。
5. **附件名归一**(实测有「附件」「附 件 1」「附件1」「附件2」)→ 规整成 `附件1`/`附件2` 之类,写进 `lib/`。
