# 17 — 文件含**多段**:年份 / 批次 / 事件按「段」建模

**What to build:** 更正票 09 的单值模型 —— 文件级只保留「**公布年份/批次**」(目录给的),**文件里含哪些段**另立表;页面把年份/批次/事件显示为**多个**。

**Blocked by:** 09(已合入)

**Status:** **implemented**(实现会话交付:代码 + 测试 + 实测证据齐;待主代理独立复核 + `oil-ui` 验收)—— **用户 2026-10-14 指出,这是票 11 的前置**

## 为什么(实测,不是设想)

一份公布文件常含多年份、多事件;**19 份经信局文件里 7 份是多段**,3 份工信部导出**全部**多段:

| 文件 | 段 |
|---|---|
| 省专 2022(145号) | 认定 2021(301)+ 认定 2022(413) |
| 省专 2024 第二批(192号) | 认定 2024/2(389,附件1)+ 复核 2021/2(67,附件2) |
| 省专 2025 第二批(30号) | 认定 2025/2(423)+ 复核 2025(260) |
| 创新型 2025 第二批(165号) | 认定 2025/2(427)+ 复核 2025(394) |
| 创新型 2026 第一批(65号) | 认定 2026/1(382)+ 复核 2023/1(75) |

⇒ **单个 `year`/`batch` 会把 192号 的「复核 2021/2」整个丢掉** —— 而票 11 要靠它把 `(事件, 年份, 批次)` 写进 `record_event`,**不修则票 11 必错**。

## 要做的

1. **新表 `stored_file_part`**:`file_id` / `title_code` / `event_kind`(award/review/maintain/nurture)/ `year` / `batch` / `attachment` / `row_count`。
2. **文件级改语义**:`stored_file` 的 `year`/`batch` **改名为「公布年份/批次」**(目录给的、单值),**别删** —— 它是「这份文件是哪一批公布的」,有意义且在列表里可排序。
3. **回填**:优先从 `record_evidence` 按 `source_file` 分组聚合得到(实测 21 份有引用、可直接用);`.doc` 那 2 份与 miit 导出留待票 11 在解析时写。
4. **页面**:年份/批次列显示**多个**(如 `2021、2022`);行可**展开**看段明细(称号 / 事件 / 年份 / 批次 / 附件 / 行数)。
5. **附件名归一**(实测有「附件」「附 件 1」「附件1」「附件2」)→ 规整成 `附件1`/`附件2` 之类,写进 `lib/`。

## 三、已知缺口 / 需要复核者注意

1. **回填覆盖了 miit 导出,与票面一句话冲突(有意的口径)**。
   票面既说「优先从 `record_evidence` 按 `source_file` 分组聚合(**实测 21 份有引用、可直接用**)」,
   又说「`.doc` 那 2 份与 **miit 导出**留待票 11」。**实测那 21 份里就包含 3 份 miit 导出**
   (18 份 jxj + 3 份 miit),两者不可兼得。取了前者:**有引用就回填**,理由是
   (a) 这才是「按 `source_file` 分组聚合」的字面实现;(b) SPEC 的「更正」一节把
   「3 份工信部导出也全是多段」当作立论依据,不回填则这条依据在页面上看不见;
   (c) 段整体派生于 evidence,票 11 解析时重写一遍也不会冲突。
   **若复核认为应严格按「miit 留待票 11」,改法是给 `backfillFileParts` 加一个 `source` 过滤,一行的事** ——
   但那会让 miit 三行在页面上没有任何段。
2. **列表的年份/批次列有显示上限**(超过 2 个只列前 2 个 + `+剩 N`,悬停给全量)。
   起因是**实测出来的溢出**:miit 导出跨 2021–2026 六七年、批次十来个,全列会把窄列撑破并压掉旁边几列。
   票面要求的是「显示多个(如 `2021、2022`)」—— 常见情形(jxj 文件 1~2 个)完整显示;
   只有 miit 那种极端情形才折叠,且**完整清单在展开的段明细里**。
3. **列名没改,只改了语义与标签**。票面说 `stored_file` 的 `year`/`batch`「改名为「公布年份/批次」」。
   本票落的是**语义 + 页面标签 + 编辑对话框标签 + schema 注释**,**DB 列名仍是 `year`/`batch`** ——
   因为票 09 的 `PATCH` 契约与它的 169 条测试都建立在这两个键上,重命名是机械但面广的改动。
   独立评审也点了这一点(注释里一度写成 `published_year`,已改正)。
   **若复核要求列名一并改,是一处纯机械改动**(schema + 迁移 + PATCH 白名单 + 页面),请指明。
4. **段的回填是「整体重建」**:遍历**全部** `stored_file` 行逐个先删后插(不只是有引用的那些),
   这样「evidence 被清掉」时残留的段会跟着清掉,而不是留一份对不上的旧段。已单测钉住。
   **代价**:票 11 若在 evidence 之外手写段,会被下一次回填冲掉 —— 请票 11 以 `record_evidence` 为准。
5. **`seriesLabel` 的 `+N` 是展示约定,不是数据**:段的完整年份/批次始终在 `stored_file_part` 里,没有丢。
6. **`EventChip` 加了一个 `hideBatch` 开关**(默认关,老用法不变):段明细里年份/批次各占一列,
   事件 chip 再带一遍就是同一行写两遍,故关掉。这是独立评审 Standards 轴第二条的处置。
