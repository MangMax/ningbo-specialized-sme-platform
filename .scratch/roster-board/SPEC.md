# 专精特新企业称号台账 · 查阅看板(规格)

> 追踪器:本地文件(`.scratch/roster-board/issues/`)。本仓未配置 issue tracker;若要发布到 GitHub/Linear,先运行 `/setup-matt-pocock-skills` 再回填。
> 词汇以 [GLOSSARY.md](../../GLOSSARY.md) 为准;关键取舍见 [docs/adr](../../docs/adr);数据模型见 [docs/data-model.md](../../docs/data-model.md)。

## 问题陈述

宁波市「专精特新」培育体系的企业名录散落在历年公布文件(DOCX/DOC)与三份工信部导出 Excel 里。经办人想回答“某个区县/某个批次有哪些企业”“这家企业现在是哪个称号、什么时候认定、有没有复核”“公布名单和工信部名单差多少”,只能手工翻文件、跨表比对,既慢又容易漏,而且每年都要重来一遍。

`20261013/` 已把原始来源归整清楚:**经信局**侧是 `省专/`、`创新型/` 两个目录的公布文件(21 份),**工信部**侧是三份导出 Excel(共 9,768 行)。缺的是:一个能快速查阅、筛选、统计、导出的工具,和一套把这些来源稳定落库、可逐年复用的数据模型。

## 解决方案

做一个 **Nuxt(SPA,不启用 SSR)单页应用**,把名录导入本地 SQLite,以**只读看板**形式提供企业名录查阅、筛选、统计与导出。

- 只读优先:本阶段不提供界面增删改(见 [ADR-只读看板先行](../../docs/adr/2026-10-13-readonly-board-first.md))。
- **记录粒度 = 企业 × 称号 × 来源**;每条记录下挂**认定 / 复核 / 维护 / 入库培育**事件,同类型可多条(见 [ADR-记录为粒度](../../docs/adr/2026-10-13-record-as-grain.md))。企业由记录按身份键归并派生。
- 身份**优先统代、缺失时按名称归并**(见 [ADR-统代优先身份](../../docs/adr/2026-10-13-uscc-as-identity.md))。
- 数据模型面向**多批次复用**:每次导入产生一个不可变**导入快照**,应用可跨快照查阅。
- 后续(非本期)在同一模型上叠加**数据管理**与**比对分析**。

## 用户故事

1. 作为经办人,我想按区县浏览企业,以便快速报出某个区的名单。
2. 作为经办人,我想按称号(小巨人/专精特新中小企业/创新型)筛选,以便分别统计各梯度。
3. 作为经办人,我想按企业名称或统一社会信用代码搜索,以便确认某家企业的称号状态。
4. 作为经办人,我想看到某家企业的**全部记录**:每个称号、每个来源、认定年份、复核年份,以便完整掌握其培育轨迹。
5. 作为经办人,我想分清认定与复核(以及工信部的维护),以便判断称号是否仍在有效期。
6. 作为经办人,我想识别“入库培育”条目,以便不把它误当作已获得的称号。
7. 作为经办人,我想看到一条记录的**出处**(来自哪份文件、哪个附件、第几号),以便回溯原始公布文件。
8. 作为经办人,我想看到区县、登记状态、当前城市,以便识别注销或已漂移出宁波的企业。
9. 作为经办人,我想看统计概览(按称号、按区县、按年份),以便快速汇报。
10. 作为经办人,我想把当前筛选结果导出为 Excel/CSV,以便交给同事或归档。
11. 作为经办人,我想看到数据质量提示(无统代、重名、非宁波、已注销),以便知道哪些需要人工核对。
12. 作为经办人,我想按来源(经信局/工信部)筛选,以便比较两侧名录。
13. 作为经办人(后续),我想对比两侧名录找出“应纳未纳/应出未出”。
14. 作为经办人(后续),我想在界面上修正企业信息并补录。
15. 作为维护者,我想每次把新的数据目录喂进导入管道就得到一个新快照,以便逐年复用而不改代码。
16. 作为维护者,我想导入是幂等的,以便重跑安全。

## 实现决策

**技术栈(全部取当前最新稳定版,由 `pnpm` 管理)**
- Nuxt `4.6`,**关闭 SSR**(`ssr: false`)。
- Drizzle ORM `0.45` + `drizzle-kit`,`better-sqlite3` 驱动,SQLite 单文件库。
- shadcn-vue `2.8` + Tailwind 组件层;Pinia Colada `1.4` 负责服务端数据;VueUse `15`;Pinia `4` 作底层 store。

**模块划分(app 只有读侧)**
- **数据契约**:`db/schema.ts`(库结构)、`db/client.ts`(打开 + 迁移)、`lib/domain.ts`(名称归一化与区县词表,与 pipeline 共享)。
- **查询层**:记录分页/筛选、按企业聚合的详情、统计、质量清单、导出数据集。
- **HTTP API**:Nitro server routes,薄封装查询层。
- **UI**:台账、统计、数据质量、企业详情。

> **不在 app 内**:解析公布文件、清洗归一化、写库 —— 属于项目外的前期工作,见 `../pipeline/`(含解析器、归一化内核与导入管道)与 [ADR-数据入库是项目外的前期工作](../../docs/adr/2026-10-13-ingestion-is-outside-the-app.md)。app 依赖里不得出现解析类库(mammoth/tinyglobby/docx 等)。

**接口契约(概要)**
- `GET /api/records?title=&source=&district=&eventType=&year=&q=&flags=&page=&pageSize=` → 分页记录列表(含企业名、称号、来源、事件摘要、flags)。`flags` 支持 `uscc_missing`(无统代)。
- `GET /api/enterprises/:id` → 企业的全部记录与事件及出处。
- `GET /api/stats?title=&district=&source=` → 计数聚合。**全部计数以记录为单位**;`byEvent` / `byYear` 数「有该事件 / 年份的记录数」,与 `listRecords` 的 `eventType` / `year` 筛选口径一致;给定 `title` / `district` / `source` 时各桶与总数一并按该条件过滤。
- `GET /api/quality?kind=uscc_missing|name_ambiguous` → 质量清单(按 `kind` 过滤;`non_ningbo` / `deregistered` 需外部富化数据,本期不产生,查询返回空)。`name_ambiguous` 由 `name_norm` 推导:同名对应多个企业或同名下多个统代。
- `GET /api/export?<同 records 筛选>` → xlsx/csv,列为 企业名称 / 统一社会信用代码 / 区县 / 称号 / 来源 / 事件 / **出处**(该记录各事件的「文件 / 附件 / 序号」汇总)。

**未决口径**
- 工信部名单批次取「维护批次」;创新型导出有 1000+ 行该字段为空(需在导入时标记而非丢弃)。

## 测试决策

**app 侧(app 仓库内)**
- **只测外部行为**:断言查询结果(条数、结果集、事件时间线),而非实现细节。
- **查询层**用直接 drizzle 插桩的 fixture 库做集成测试(不经过导入管道 —— 台账是只读的,测试造数就该直接建读模型):`tests/query.test.ts`、`tests/export.test.ts`。
- **库引导**:`tests/db.test.ts` 断言迁移可应用、称号字典幂等、记录唯一约束。
- 无 UI 单测;看板以真实库人工验证。

**pipeline 侧(项目外,`../pipeline/`)**
- 归一化内核纯函数单测(统代/名称/批次/区县清洗)。
- 解析器 + 导入管道用合成 fixture docx 驱动,断言归一化计数、事件类型分布、`.doc` 与 `.docx` 一致、多段名单切分、**幂等**(同 label 重跑逐表行数不变)。
- **交叉校验**:解析计数与 `公布文件名单全部整理版.xlsx` 比对,作为回归基线。
