# 01 — 归并安全阀 + 回填可信化(pipeline)

**What to build:** 让 `pipeline/src/enrich.ts` 的**统代回填与同一法人归并**只接受**可证的证据**。这是本次数据错误的治本点。

**Blocked by:** —

**Status:** done

## 现状(已查明,别再猜)

`backfillUsccFromCollated`:

1. **遍历整理版全部 sheet**,按企业名 `uniqBy` **取首次出现** —— 创新型 sheet 在前,于是**它对同时出现在两 sheet 的名字,用错了那张表的统代**(见 SPEC 根因 1、2)。
2. 回填时若该统代**已属于另一家企业**,代码判为「两个独立来源对同一信用代码达成一致 ⇒ 同一法人」并**自动归并** —— 但这里是**单一来源**,前提根本不成立(见 SPEC 根因 3)。

## 要做的三件事

### (1) 归并只认两个**原始**来源

- 归并的唯一合法依据:**公布文件 + 工信部导出**对同一统代达成一致。
- **整理版(推算/手维护)一律不得触发归并。**
- 落实:把「回填」与「归并」在代码里**彻底分开** —— 回填只写 `uscc_norm`,**绝不**调用合并;合并只由「两原始来源一致」的路径驱动。

### (2) 回填必须是**有据可依**的

- 回填前先问:**这家企业真的不在工信部名单里吗?** 若它在工信部任一名单里(哪怕写法差一个「宁波」前缀,见票 02),就**不该回填**,应以工信部统代为准。
- 回填得来的统代必须能**独立佐证**(同一名称在另一处原始来源也这么写);不能佐证 → **不写**,保持无统代 + `uscc_missing`。
- 若回填的统代**已被另一家企业占用** → **不合并**、不删除任何主体;标记冲突(建议 `uscc_conflict` 或复用 `name_ambiguous`)并列入待确认。

### (3) 记录归并依据,可审计

- 每次归并输出:**被并方 / 并入方 / 统代 / 依据来源(哪个文件、哪一行)**。
- 这份输出是票 04 审计的输入。

## 测试(必须,用 fixture)

- [x] **反例锁死**:一个企业无统代、只在**整理版**里出现(或整理版给的统代已属他人)→ **不得**发生任何归并;该企业仍存在、仍无统代、带标记。
- [x] 两个原始来源(公布文件 + 工信部)对同一统代一致 → 归并发生,并输出依据。
- [x] 回填不得覆盖企业已有的(工信部)统代。
- [x] 一个「贝兹德式」fixture:整理版把 A 的统代错填成 B 的 → 断言 **A、B 仍是两个主体**,记录不迁移。
