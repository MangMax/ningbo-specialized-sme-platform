# 名录对比、年度更新与清理入库规格

## Problem Statement

用户需要依据经信局正式公布文件维护专精特新、小巨人和创新型中小企业的称号历史，同时利用工信部平台导出表和两个查询接口解释现存平台状态。当前信息分散在称号记录、导出表和查询结果中，跨称号去重、来源追溯、差异原因及年度更新难以在一个视图里确认；文件清理入库也缺少稳定、统一、可回放的 API 路径。

## Solution

把公布文件、平台导出快照和接口查询证据作为不同来源保留，以企业为总表粒度、以称号认定/复核事件保存历史。利用工信部两个查询接口的完整关系记录核查平台差异。代理依据原始关系文本识别经信局侧曾用名和其它可证实原因；确认主体后回填统一社会信用代码并保存曾用名，按原因记录对应的后续措施。系统不建设模糊推断引擎。提供一张跨称号去重的企业视图，展示平台差异、原因、措施、证据、称号历史及来源页码；用户可查看并按现名或曾用名搜索。后续年度可导入最新公布文件和三张平台导出快照，预览后增量更新。清理代理通过统一 API 写入文件、OCR/解析结果、企业、曾用名、称号事件、来源证据和平台快照。

## User Stories

1. 作为名录维护者，我希望所有公布文件中的条目都进入正式名录，即使它们暂时无法匹配平台导出，以免把真实公布记录误删。
2. 作为名录维护者，我希望一份包含多个称号或认定/复核附件的公布文件能保留每个称号事件，而不是把附件或批次折叠成一条。
3. 作为名录维护者，我希望把历年小巨人工作簿按批次导入，并按约定将第一批映射为 2019、第八批映射为 2026。
4. 作为名录维护者，我希望同一企业跨批次重复出现时企业只保留一份身份，但每次正式称号事件都保留下来。
5. 作为名录维护者，我希望三张工信部导出表被记录为某次平台现状快照，而不是覆盖正式公布历史。
6. 作为对比使用者，我希望跨称号查看时同一企业只出现一次，并能展开查看它的全部称号、批次和认定/复核事件。
7. 作为对比使用者，我希望公布名单有而平台缺少、平台多出而公布名单缺少的记录都能被筛选，并看到计数单位。
8. 作为对比使用者，我希望平台两个接口返回的多条关联关系都被保留，且平台明确记录的经信局侧别名能帮助匹配。
9. 作为名录维护者，我希望把经信局公布名称与工信部关系中明确记录的经信局曾用名进行候选匹配，以便为改名企业补回统一社会信用代码。
10. 作为名录维护者，我希望确认匹配后将曾用名和来源关系写入对应企业，保留名称值、来源证据、核验状态和可获得的时间信息。
11. 作为名录使用者，我希望企业曾用名作为企业身份历史可查看，并且按现名或曾用名搜索都能找到同一企业。
12. 作为对比使用者，我希望每个差异原因都能看到接口证据和对应的后续措施：外迁、注销、更名、平台未更新和迁入分别处置；迁入时能追溯原城市、称号、年份和批次。
13. 作为名录维护者，我希望接口查询失败、没有查询、查询无记录和确认无差异原因是不同状态，避免把失败当成无记录。
14. 作为名录维护者，我希望先用平台关系中的曾用名匹配缺少统一社会信用代码的公布企业，再对仍未解决的企业逐项通过公开来源查证并记录出处；证据不足时宁可留空并待核实。
15. 作为年度更新操作者，我希望导入最新公布文件和三张新导出表前先看到新增、更新、移除和待核实数量，再决定应用。
16. 作为年度更新操作者，我希望仅由历史平台导出带入、从未出现在任何正式公布名单的企业，在最新平台快照不再出现时从当前企业总表移除。
17. 作为年度更新操作者，我希望平台消失不会删除正式公布历史，且重复执行同一年度输入不会重复增加企业或事件。
18. 作为补贴筛选使用者，我希望按企业 × 称号看到最早的正式认定及来源，复核失败后再获批不被误标为首次认定。
19. 作为复核安排使用者，我希望快速得到下一年到期的有效称号清单，并看到计算所依据的最近认定/复核事件。
20. 作为名录使用者，我希望从企业或称号记录的页码直接打开原文件预览并定位到对应 PDF 页面。
21. 作为清理代理，我希望 PDF 先转成页图后并行提交 OCR，多个 PDF 也可并行处理；Word、Excel 等文字格式直接解析。
22. 作为清理代理，我希望 OCR 与三张导出表匹配后只对需要校验的页做视觉复核，但最终仍保留并入库完整公布名单。
23. 作为维护者，我希望以后新增文件、OCR 结果、纠偏后的称号记录、曾用名、来源证据及平台快照通过同一可审计 API 写入并可安全重放。
24. 作为文件管理者，我希望上传名、展示名、稳定文件身份和物理路径的关系清晰，改名不破坏 OCR、出处或预览链接。

## Implementation Decisions

- 经信局公布文件及其附件是称号、认定/复核事件与批次的权威来源；工信部三张导出表表示采集时点的平台状态。
- 企业总表按企业去重；企业可同时具有多个称号，每个称号可有多次认定/复核事件。不同称号或批次不能因企业去重而丢失。
- 企业曾用名是关联到企业身份的领域记录，不作为另一家企业或仅存在于临时匹配备注。记录保留曾用名原值、其来源接口/关系证据、核验状态，以及来源中实际提供的时间信息；来源未提供的生效时间不推测。
- 年度导出需保留导入时间、来源文件身份和版本；相同来源重放幂等，新版本可与旧快照比较。
- 两个平台接口的核查以代理阅读原始关系与名称为主，不建设模糊推断规则引擎；产品提供证据查看、匹配确认、数据回填和查询能力。对缺少统一社会信用代码的公布记录，代理检查两个接口返回的完整关系集合，使用其中明确标注的经信局侧曾用名识别候选；确认后回填有效统一社会信用代码，并建立有关系来源的曾用名记录。不能因关系冲突、同名多主体或证据不足而自动合并；歧义项进入待核实。
- 企业曾用名可在企业详情中查看，并纳入企业名称搜索；搜索现名或任一已确认曾用名都返回同一企业身份。
- 两个平台接口的多条关联分别保留。差异解释记录原因、原始关系证据、核验状态及后续措施。已知原因及措施包括：外迁记录迁出状态并保留正式历史；注销记录主体状态且不删除公布历史；更名更新可确认的当前名并将旧名保留为曾用名；平台未更新保留正式名录并标明平台时点；迁入记录来源城市、称号、年份及批次。核查发现的新原因可以扩展，但必须有证据并说明后续措施；不确定状态进入待核实。
- 外地迁入原因在证据充分时显示原称号、年份及批次。公布历史从不因平台导出缺失而删除。
- 复核周期按用户确认的三年规则计算；复核未通过后不列入当前有效资格的复核清单，重新获批刷新下一次到期时间但不重置首次认定。
- PDF 来源页码采用 PDF 实际页序；没有稳定页面概念的格式保留空页码。预览跳转必须指向同一来源文件身份。
- 文件/OCR/解析及名录数据逐步统一由应用 API 写入；TUS 仅负责可续传传输，不单独定义业务文件身份或重命名语义。
- 核对工作簿时发现当前数据含第 1 至第 7 批；当前文件未提供第 8 批，不能造出空的第八批记录。批次年份约定为 2018 加批次序号。

## Testing Decisions

- 好的测试验证用户可观察的行、状态、原因、证据和更新结果，不依赖内部函数名称或实现结构。
- 主验收接缝沿用现有比对 API 到比对页的真实数据流，以 SQLite 场景数据覆盖多称号、重复批次、公布名称与平台现名不同但关系中存在经信局曾用名、单一/多条关系、代理确认与歧义候选、曾用名写入与按现名/曾用名搜索、外迁/注销/更名/未更新/迁入及各自后续措施、可扩展的其他原因、接口失败和计数。
- 导入/API 通过公开 HTTP 契约验证来源身份、预检、幂等重放、完整名单保留和失败可诊断性。
- 首次认定与复核清单通过完整历史事件输入验证，包含复核通过、复核失败后再次获批及缺少早期历史。
- 页码跳转通过真实预览交互验证目标文件及 PDF 页码，覆盖附件边界和无页码格式。
- 现有相近测试先作为回归基础：comparison 差集、reconcile 解释、导入/API、文件预览/页图库与 OCR 工作台。UI 验收仍需在应用页面实测。

## Out of Scope

- 不以平台导出表覆盖或改写正式公布历史。
- 不因 OCR/名单未匹配平台导出而丢弃正式名单条目。
- 不根据文件名、地址或低置信度名称猜测信用代码、身份合并、年份或批次。
- 不在本规格中自动判定补贴资格金额或取代人工处理证据冲突。
- 不在文件身份策略确定前改变当前 TUS 落位规则。

## Further Notes

- 当前页面已有比对 API 和解释展示，但平台解释缓存缺失时会显示空解释；需区分当前已经交付的行为与本规格新增的持久化查询证据。
- 用户优先级为：准确对比及原因解释、之后的名录使用能力和清理流程；文件命名规则排在后续。
- 当前规格与票面已按用户确认的测试接缝整理；代理先核查两个接口中的关系与曾用名，网络补查仅处理仍无法匹配的项目。
