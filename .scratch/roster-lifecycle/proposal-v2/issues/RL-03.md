# [P0] RL-03 — 记录双接口差异原因、曾用名与后续处置

**级别：** scope:L — 接口关系、企业身份/曾用名、差异处置与用户查询跨数据模型、API 和页面；本票跟踪以下可独立验收的小切片，不做一个大 PR。
**难度：** 高｜**主要难点：** 多条关系的别名证据必须保真，确认后回填不能误并企业｜**建议模型：** magpie + DeepSeek（高推理）

## Parent

[总规格 #14：专精特新企业名录规格](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/14)

## What to build

代理或名录维护者能查看工信部两个查询接口返回的完整关系记录，依据原始文字核实经信局公布名与平台关系中的曾用名，并解释平台差异。确认主体后回填统一社会信用代码、写入来源可追溯的曾用名，并按已证实原因记录合适的后续措施。此流程由代理阅读和判断证据，产品不实现模糊推断引擎。

## 实施拆分（每项不超过 scope:M）

- [ ] 保留两个接口的完整关系与源文本，并提供可追溯核验记录。
- [ ] 通过统一 API 保存代理确认的曾用名、信用代码、差异原因、证据和后续措施。
- [ ] 在现有名录查询/详情接缝验证现名、曾用名和已核验处置可被查看与查询。

## Acceptance criteria

- [ ] 两个接口返回的全部关联、申报关系及原始名称均可查看；一个信用代码对应多条关系时逐条保留。
- [ ] 对缺少信用代码的经信局公布记录，代理可依据接口关系中明确标注的经信局曾用名识别候选；确认主体后回填有效统一社会信用代码。
- [ ] 更名确认后，将经信局公布名/已证实旧名作为企业曾用名记录，保存来源接口、关系证据、核验状态和可获得的时间信息；现名和曾用名均可查询。
- [ ] 外迁、注销、更名、平台未更新、迁入等已证实原因均保存原因、来源记录、核验状态和相应后续措施；新发现的原因可扩展记录，不强塞进不准确的既有类别。
- [ ] 迁入记录来源城市、原称号、年份和批次；证据缺项时明确留空/待核，不猜填。
- [ ] 后续措施与正式历史规则一致：外迁或注销更新当前状态但不删除公布历史；更名保留名称沿革；平台未更新不误删正式名录；迁入保留来源沿革。
- [ ] 回归用户给出的 91330211255994457P 案例：能够匹配经信局侧曾用名，且展示该信用代码的全部关联关系。
- [ ] 同名多主体、关系冲突或不能确认的候选不自动回填，保留为待核实状态。
- [ ] 查询失败、未查询、无记录和已确认无差异原因分别显示，不互相冒充。
- [ ] 不增加模糊匹配/原因推断规则引擎；以真实接口响应、SQLite 场景数据和比对页行为验证证据、确认、回填、原因措施和查询结果。
