**难度：** 高｜**主要难点：** 批次重放和部分失败时保证来源证据、称号事件和企业状态不静默错账｜**建议模型：** magpie + DeepSeek（高推理）

## Parent

[总规格 #14：专精特新企业名录规格](https://github.com/MangMax/ningbo-specialized-sme-platform/issues/14)

## What to build

清理代理和年度更新流程能通过应用公开的 API 写入 OCR/解析结果、纠偏后的企业、已确认的曾用名、接口差异原因与后续措施、称号事件及来源证据，不再直接写正式数据库或依赖彼此不同的导入器。各功能可保留符合本领域的 API 契约；本票负责把清理代理的完整流程统一改为调用应用 API。

## 实施拆分（每项不超过 scope:M）

- [ ] 提供批次预检与带来源身份的 API 写入契约。
- [ ] 验证幂等重放、逐项错误、部分失败恢复和写入结果查询。
- [ ] 将现有清理代理流程接入该 API，保留完整名单和源文件/OCR 证据。

## Acceptance criteria

- [ ] API 接受带来源身份的清理/导入批次，并返回可操作的预检结果。
- [ ] 一个批次可提交企业、带来源证据的已确认曾用名、差异原因和后续措施、称号事件及来源证据；平台快照和解释可由同一契约安全写入。
- [ ] 重复提交同一来源幂等；部分无效行返回逐项错误，不能静默丢行。
- [ ] 应用后可查询已写入数量、待核条目、失败项和来源关联。
- [ ] API 有鉴权；凭证仅从运行环境读取，不写入仓库、数据库内容或运行日志。
- [ ] 现有清理流程可作为该 API 的客户端运行，完整名单包含未匹配平台导出的条目。
- [ ] 以真实 HTTP 契约测试预检、提交、重复重放、失败恢复及完整性，不以直接数据库写入代替 API 验收。
