# 名录对比、年度更新与清理流程路线图

日期：2026-10-15。票据索引见 [`issues/README.md`](issues/README.md)。

## 业务事实

- 经信局公布文件是称号认定、复核及批次的权威来源。工信部三张导出表反映平台当前记录，只作为对照快照；不能用它们改写历史公布名单。
- 企业总表按企业去重；称号、认定/复核事件、批次及证据分别保留。一个企业可以同时属于多个称号，也可以跨批次重复出现。
- 平台两接口用于核实差异成因和关联关系。迁入、迁出、注销、平台信息未更新、未公布等要附查询证据；外地迁入应记录原称号、认定年份和批次。解释不确定时保留待核实状态。
- OCR/名单与导出表未匹配属于正常业务情况，不作为丢弃名单记录的理由。正式名单所有条目都必须进入企业及称号历史；匹配结果用于校验和解释。
- 名称别名是匹配证据，不是独立企业身份。信用代码优先；名字、地址或单一外部来源不足以自动合并有歧义的企业。
- 年度更新读取最新公布文件和最新三张导出表，形成增量变化。仅由历史平台导出引入、从未出现在公布名单的企业，若不在最新导出中，应从当前企业名单移除；官方历史事件不能因平台变化而删除。
- 首次认定按企业 × 称号的最早正式认定事件判断。复核通过不算新的首次认定；复核失败后再次获批也不重置首次认定。
- 三年复核清单按称号历史计算。失败复核不再进入当前有效资格的复核队列；重新获批会刷新下一次复核到期时间，但不改变首次认定标记。

## 分阶段目标

1. 先形成可审阅的数据模型与差异规则，解决三称号去重、平台多关联/别名匹配、解释证据和年度导出快照的边界。
2. 再交付统一企业视图：公布名单与当前平台差异、原因、迁入原称号与批次、历史事件和来源页码。
3. 加入首次认定、下一年复核清单和文档页码跳转等高频使用功能。
4. 固化 API 写入路径和代理清理流程，完成本次缺信用代码补查。
5. 文件存储命名/重命名作为低优先级决策票处理。

## 已核对的新增小巨人工作簿

源文件：`../../经信局名单/小巨人/经信局公布历年小巨人企业名单.xlsx`。

- 工作簿只有一个工作表，511 条有企业名称的数据；信用代码有值。
- “批次”列现有值为第 1 至第 7 批，没有第 8 批。按约定年份为 `2018 + 批次序号`，所以现有行映射到 2019–2025；如果以后出现第 8 批则映射到 2026，当前文件没有第 8 批数据。
- 同一信用代码 `91330211316904639T` 出现两次，分别为第 2 批与第 6 批，应保留两条称号事件并在企业总表去重。
- 工作表有 39 列；名单字段位于 A:J，K 之后还混有备注、行业及其他名单数据。导入只读取 A:J，不把后续横向数据误当名单行。

## 当前上传与 API 事实

- 最新 app 主线提供 TUS `/api/uploads`、文件登记 API、页图/OCR/任务 API、MCP 文件/OCR/段写回工具。代理应先从 app 的 OpenAPI/MCP 工具定义读取实际契约。
- 已核对的 app 主线尚无统一的企业/称号事件/平台快照写入 API；当前 pipeline 的名单入库仍有 CLI/导入器路径。票 RL-11 负责补齐统一 API。在它交付前，不能把直写数据库或自制脚本描述成已统一的 API 流程。
- TUS 只处理断点续传。当前服务端把文件放在 `files/<source>/<kind>/<year>/<batch>/<filename>`，保留上传文件名；同目录同名时追加 ` (n)`，并返回真实落位路径。它不规定业务命名规则。
