# RL-01 — 对比与生命周期数据模型决策

- **级别**：`scope:XL`（领域模型、数据迁移和 API 边界变化）
- **优先级**：P0
- **难度**：高｜**主要难点**：将公布历史、平台当前快照和迁移解释分开，同时支持回放且不丢历史｜**建议模型**：magpie + DeepSeek（高推理）
- **状态**：ready
- **阻塞项**：无

**为什么现在做**：如果把公布名单和平台导出混成一张当前表，跨称号去重、历史认定、迁入原因和年度删除都会互相污染。**风险**：过早定表可能把临时解释固化成历史事实；先交 ADR 并拆出实现票。

## 目标

为三类称号建立一个共同的企业身份与历史视图，明确公布名单、平台当前导出、平台接口解释之间的关系，作为后续表/API/UI 票的唯一契约。

## 范围

- 定义唯一企业、名称/别名、称号资格、认定与复核事件、来源文件/附件/页码、年度平台导出快照、平台关联记录及解释证据的最小关系。
- 规定以公布文件为历史称号权威；三张工信部导出是带时间/文件身份的当前平台对照源。
- 定义 `businessList` 与 `applyList` 多条关联、同名候选、跨地迁入和迁出、注销、未更新、未公布、无信用代码、待核实等解释的证据与状态。
- 定义三年复核周期、首次认定、复核失败后再获批、平台单独出现企业移除当前总表的生命周期语义。
- 写数据迁移/回填方案和不确定记录的处理边界；保留同一企业跨称号、跨批次事件。

## 验收

- ADR 给出概念 ER 图、关键唯一键、历史/当前数据边界、迁移步骤和 API 责任边界。
- 明确哪些是已验证事实、哪些是待人工确认；不把名称猜测写成自动合并规则。
- 至少覆盖：多称号同一企业、同信用代码多批次、迁入企业原称号年份批次、复核失败后再获批、平台查询返回多条关系。
- 从 ADR 拆出独立实现票后再改 schema/API/UI。

## ADR 必须拆出的实现切片

- **数据与迁移**（≤M）：企业、称号事件、导出快照、接口证据和解释状态的最小 schema 与迁移计划。
- **写入/API 契约**（≤M）：统一写入批次、幂等、预检和来源身份。
- **读取/产品视图**（≤M）：一企一行与事件时间线/平台差异的查询契约。

## 不在本票

不导入数据、不改正式数据库、不实现模糊匹配、不直接做全页面重构。
