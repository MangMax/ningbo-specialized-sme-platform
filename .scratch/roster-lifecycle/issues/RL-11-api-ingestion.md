# RL-11 — 统一名单数据 API 写入路径

- **级别**：`scope:L`（跨文件服务、数据契约和 pipeline 写路径）
- **优先级**：P1
- **难度**：高｜**主要难点**：跨企业、事件、证据和快照的批次事务/幂等写入，避免新旧导入器并存错账｜**建议模型**：magpie + DeepSeek（高推理）
- **状态**：ready
- **阻塞项**：RL-01

**为什么现在做**：当前文件/OCR 与正式名单写入路径不统一，后续年更需要一个可审计入口。**风险**：部分提交、重复批次或凭证泄露；先锁契约，再迁移调用端。

## 目标

让文件、OCR、纠偏后的企业/称号事件、平台快照和解释写入统一通过 app 对外 API/MCP 契约，不再由不同导入器直接写 SQLite。

## 已有边界

app 主线已有 TUS 文件上传、文件登记、PDF 页图、OCR 结果、解析段、任务 API 和相应 MCP 工具；名单实体/事件/平台快照尚无统一写入 API。请补齐缺口并复用现有能力，不重造第二套数据库写路径。

## 验收

- 发布可发现的 API 契约，支持一个有来源身份的导入批次写入企业/别名/称号事件/证据/平台快照与解释。
- 批次提交有幂等键、预检与结果摘要；重复调用不会重复企业或事件，错误返回逐项可修复信息。
- 写路径有鉴权；密钥只从运行时凭证读取，不落库、不进仓库、不进入运行日志。
- `roster-ingestion-pipeline` skill 可从 API/MCP 实际发现并调用这条路径。
- 现存 CLI 可退化为 API 客户端；生产写入不再绕过 API 直写正式库。

## 实施切片（每项 ≤M）

- 定义导入批次 API 与只读预检/幂等键契约。
- 实现单批事务写入和逐项结果/失败报告。
- 将现有 pipeline 调整为该 API 的客户端并验证重放。
