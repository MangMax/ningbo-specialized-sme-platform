# RL-13 — TUS 文件标识、命名与重命名策略

- **级别**：`scope:spike`（规则未决，先 timebox 调查，不合并生产代码）
- **优先级**：P2
- **难度**：中｜**主要难点**：改名可能影响已存证据路径、OCR 和重复文件识别｜**建议模型**：magpie + DeepSeek
- **状态**：ready
- **阻塞项**：RL-11

**为什么现在做**：用户询问上传名、存储规则和重命名后的处理。**风险**：把 TUS 传输 ID 当业务身份或直接改磁盘名会断开证据引用。

## 当前实现事实

TUS 是断点续传协议，不规定业务文件夹和文件名。当前 app 在上传完成后按 `files/<source>/<kind>/<year>/<batch>/<filename>` 落位，保留上传时文件名；同目录撞名追加 ` (1)`、` (2)` 等后缀，并回传实际相对路径。`.incoming/` 只保存传输期间的分片。

## 目标

确认文件路径、用户显示名称、原始上传名和稳定文件身份之间的规则，避免重命名破坏证据关联或覆盖历史文件。

## 决策内容

- 是否用稳定 file ID/content hash 作为内部身份，原始名仅作展示/下载名。
- 上传前改名、上传后改名、同名不同内容、同内容不同名、替换文件时如何操作。
- `stored_file.rel_path`、OCR/页图、证据链接和下载名怎样同步；改名是否保留旧名别名与审计轨迹。

## 验收

- 输出一页决策和迁移影响；优先不改变现有上传协议与已存证据。
- 给出用户可执行的重命名流程，以及同名/重复内容的明确提示。
- 未完成决策前不更改 TUS 落位规则。
