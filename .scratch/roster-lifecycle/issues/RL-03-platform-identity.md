# RL-03 — 平台双接口关联与别名匹配证据

- **级别**：`scope:L`（外部接口、身份解析和展示契约）
- **优先级**：P0
- **难度**：高｜**主要难点**：业务接口返回多条关系且有 HTML 响应，别名必须避免误合并｜**建议模型**：magpie + DeepSeek（高推理）
- **状态**：ready
- **阻塞项**：RL-01

**为什么现在做**：平台接口多关系与别名漏配会直接制造错误差异。**风险**：会话过期或弱匹配被误判成平台无记录；失败、无记录和待核实必须区分。

## 目标

用工信部两个接口解释公布名单与平台导出之间的差异，完整保留一个企业返回的多条关联关系，并正确利用平台记录中的别名。

## 范围

- `POST /zxqy/ZjtxxjrBusInfoManageBLH/businessList` 按称号查询企业关联信息；当前接口返回 HTML 表格，需要按真实结构解析。
- `POST /zxqy/YzzxqyApplayBLH/queryList` 分页查询申报记录。缓存查询时间、接口来源、企业/称号、原始关联项和解析结果。
- 先按校验通过的统一社会信用代码关联；再使用有来源支撑的企业别名。多条记录全部保留并分别说明匹配依据。
- 回归案例：工信部信用代码 `91330211255994457P` 的多条关联中，平台记录明确写有经信局侧别名，应能关联到对应企业并展示所有关系。
- 接口会话失效或返回结构异常时，显示查询失败/待核实，不把失败当“平台无记录”。

## 验收

- 结构化结果可追溯到接口、查询时间、原始字段和匹配方式。
- 指定 USCC/别名案例匹配成功；别名有歧义时不自动归并，进入人工清单。
- 同一企业的多个平台关联不被覆盖为一条；重复查询可按缓存/刷新规则重用，不丢历史证据。
- 5 个抽样差异能由接口证据支持或明确标为未解释，不能用猜测填成注销/迁入。

## 实施切片（每项 ≤M）

- 接口适配与 HTML/分页解析、失效态识别。
- USCC/别名候选匹配与指定案例回归。
- 证据写回、缓存刷新和页面解释呈现。
